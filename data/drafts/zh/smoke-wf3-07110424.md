# 三家 AI coding agent 怎么管上下文：Claude Code × Codex × Cursor 入门对照

**一句话价值**：上下文管理不是某个工具的私房技巧，而是所有 coding agent 共享的一门手艺。看懂 Claude Code、OpenAI Codex、Cursor 三家在解同一个问题——上下文窗口「有限，而且会随填满而退化」——你换工具就不用从头重学。

**谁该读**：会用 Claude Code / Cursor / API、能跑通脚本，但不是 systems engineer 的 AI builder。你不需要读懂 harness 源码，只需要在每次对话里知道「留什么、丢什么、隔离什么」。深水区（7 层记忆架构、源码级实现）本文只做一句话旁注 + 外链，浅读者可以在任意小节停下。

> **本文的工作论点（编辑立场，非作者亲笔署名观点）**：市面上「Claude Code 上下文管理教程」已经很多，但几乎都锁死在单一工具。真正能迁移的认知是——三家用不同机制解**同一个**结构性问题。把这层看穿，工具切换的学习成本会塌下去一大半。

## 一、先装进脑子的底层事实：上下文有限，而且会腐烂

**定义**：上下文窗口（context window）是模型一次推理能「看到」的全部 token——系统提示 + 对话历史 + 所有工具调用与输出 + 你让它读过的文件。**上下文管理 = 在这个有限、且会随填满而退化的窗口里，主动决定留什么、丢什么、隔离什么。**

入门读者只要先接受两条硬事实，后面所有操作就不是死记硬背：

**事实 1：上下文是「有限、且边际递减」的资源，不是越大越好。** Anthropic 在官方工程博客里把它称作模型的**注意力预算（attention budget）**——每多塞一个 token，都在花掉这份预算，而不是白赚（来源：[Anthropic，《Effective context engineering for AI agents》，2025-09-29](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。原因在 transformer 的结构里：token 之间要两两建立关系，规模随长度呈 n² 增长，窗口越长，每个 token 分到的「注意力」越稀。

**事实 2：退化是实证现象，不是玄学。** Chroma 的一项研究测了 **18 个主流模型**（含 GPT-4.1、Claude 4、Gemini 2.5、Qwen3），结论一致：**输入越长，表现越差——即使任务本身很简单**。更反直觉的是，退化早在窗口触顶之前就开始了，而且一个不相关的干扰项，会随上下文变长而放大它的伤害（来源：[Chroma，《Context Rot》，2025-07-14](https://www.trychroma.com/research/context-rot)）。

把这两条合起来，就是一句可以贴在显示器上的话：**你的目标是信噪比，不是填满。** 1M 的窗口不是让你不用管上下文，而是给你更多时间，在模型变笨之前主动干预。

## 二、同一个问题：三家都要回答「留什么、丢什么、隔离什么」

一旦接受「有限 + 会腐烂」，每个 coding agent 就都被逼着回答同三个问题。这三个问题，就是你看任何一家工具的心智地图：

- **留什么**——哪些历史值得保留？怎么在不撑爆窗口的前提下带着它走？
- **丢什么**——哪些中间过程、失败尝试、工具垃圾输出，应该主动清掉？
- **隔离什么**——哪些活可以扔到一个独立窗口里做，只把结论带回来？

下面这张表是本文的骨架。三列是三家工具，三行之外还藏着一条「隐形的第六招」，第六节会单独讲：

| 维度 | Claude Code | OpenAI Codex | Cursor |
|------|-------------|--------------|--------|
| 压缩（留什么的浓缩版） | `/compact`（有损，可加方向）+ 7 层自动微压缩 | 超阈值自动压缩，返回带 `encrypted_content` 的 compaction item | 对话过长则窗口填满，直到没有空间继续回应 |
| 清空 / 新开（丢什么） | `/clear`（你写 brief，精准重启） | 开新 thread | 开新 chat |
| 回退（丢掉失败尝试） | `/rewind`（`esc esc`） | —— | —— |
| 隔离 | subagent 独立 context window | Codex 侧本文未取到对等原语 | Skills 动态加载 vs Rules 常驻 |
| 缓存纪律（隐形第六招） | 保持 prompt cache 前缀稳定 | 别中途改 `AGENTS.md`，会失效系统提示缓存 | `.cursor/rules/*.mdc` `alwaysApply:true` 常驻吃 token |

> [!note] 关于本文的核验状态
> Claude Code 一栏的机制来自已核验的一手源（见文末来源）。Codex 与 Cursor 两栏的部分细节来自官方页面的二手交叉，**尚未逐字核验**——凡涉及具体机制名（如 `encrypted_content`、`alwaysApply`）之处，我都标注了官方出处，读者可自行回源确认。

如果你把这张表读懂了，剩下五节只是把每一行讲深一点。

## 三、压缩（compaction）：三家怎么把长历史浓缩成短状态

**结论先行**：压缩就是「留什么」的自动化——当历史太长，工具替你把它浓缩成一份更短的状态，腾出窗口继续干活。三家的差别在于**浓缩成什么形态**。

**Claude Code** 给你两个手动开关和一层自动兜底：
- `/compact` 让模型自己决定什么重要（有损），但你可以加方向：`/compact 聚焦鉴权改动，丢掉测试调试`。
- 底层还有一套自动的微压缩，会在每一回合前清掉旧的工具结果、把大文件读取只留预览（来源：[Troy Hua 对 Claude Code harness 的逆向分析，2026-04-01](https://x.com/troyhua/status/2039052328070734102)）。

**OpenAI Codex** 的做法有一个入门读者值得记住的差异点：它超过阈值会自动压缩，而压缩返回的不是一段「总结文字」，而是一个带**不透明 `encrypted_content` 的 compaction item**——保留的是模型的潜在理解状态，而不是人类可读的摘要（来源：[OpenAI，《Unrolling the Codex agent loop》，2026-01-23](https://openai.com/index/unrolling-the-codex-agent-loop/)；另见官方博客对 Codex 执行循环的说明：[Run long-horizon tasks with Codex](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)）。对比之下，Claude 的 `/compact` 是「总结成文字」，Codex 是「保留潜在状态」——同一个动作，两种哲学。

**Cursor** 在公开文档里的表述更朴素：对话太长时，窗口会一直填到没有空间继续回应（来源：[Cursor Docs](https://cursor.com/docs)）。它更依赖你主动开新 chat，而不是一个显式的压缩命令。

对入门读者的行动项：**别等自动触发再压缩。** 在上下文还健康、模型还聪明的时候主动压，并且加一句方向说明——因为模型在窗口最满、最笨的时候，恰恰最不擅长判断什么该留。

## 四、隔离（subagent / Skills）：把中间过程挡在主窗口外

这一节最容易被误解，所以先把结论钉死：**subagent 的核心价值是上下文隔离，不是并行。**

很多人以为开子 agent 是为了「同时干好几件事」。真正的价值在别处——凡是不需要主 agent 亲自推理的活（批量机械操作、限定范围的调研、可并行的探索），都丢给一个**独立窗口**去做，只把结论带回主窗口。中间那一大堆工具输出、试错、噪音，全部挡在主窗口之外（来源：[Boris Cherny（Claude Code 创造者）谈隐藏特性与 subagent 用法](https://x.com/bcherny/status/2038454336355999749)）。

一个可以随手用的判断反射：**「这一步之后，我还需要那些工具输出本身吗，还是只需要那个结论？」** 只需要结论 → 丢给 subagent。

三家的平行版本：
- **Claude Code**：具名 subagent（如 `code-simplifier`、`verify-app`），各自跑在独立 context window 里。
- **Cursor**：Skills **动态加载** vs Rules **常驻**——Skills 只在需要时才进窗口，是「用完即走」的隔离思路；这正是 Claude「按需检索（just-in-time retrieval）」的跨工具平行版（来源：[Cursor Agent Best Practices](https://cursor.com/blog/agent-best-practices)）。
- **Codex**：本文这轮调研未取到与 subagent 对等的一手原语，暂不下硬结论。

如果你想给这套隔离思路配一套干净的词汇，Simon Willison 的三分类很好用：**context quarantine（隔离）/ pruning（修剪）/ summarization（摘要）**（来源：[Simon Willison 的 context-engineering 标签页](https://simonwillison.net/tags/context-engineering/)）。

## 五、隐形的第六招：保护 prompt cache（成本差 ~200x）

前面五招都在管「窗口里放什么」。还有一招不在窗口里，却直接决定你的账单——**保护 prompt cache（提示缓存）。**

**定义 + 数字**：主流 API 会把提示前缀（prefix）在服务端缓存住（TTL 约 1 小时）。在 20 万 token 的上下文下，一次**缓存命中约 \$0.003，一次缓存未命中约 \$0.60——相差约 200 倍**（来源：[Thariq，《Lessons from building Claude Code: prompt caching is everything》，2026-04-30](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)）。Anthropic 内部甚至把缓存命中率当作 SLO，命中率掉了会开 SEV 事故单——足见这条有多硬。

关键在于：**缓存命中的前提是前缀字节完全一致。** 你在 session 中途改动系统级文件，前缀就变了，整段缓存作废，下一次请求按未命中计价。于是同一条纪律，在三家工具上投影成三句话：

- **Claude Code**：系统竭力保持 API 前缀逐字节稳定，连子 agent 都继承父 agent 的完整前缀来保命中（来源：Troy Hua 逆向分析，同上）。
- **OpenAI Codex**：官方明确提醒——**别在会话中途改 `AGENTS.md`**，那会失效系统提示的 prefix cache（来源：[OpenAI，《Unrolling the Codex agent loop》](https://openai.com/index/unrolling-the-codex-agent-loop/)）。
- **Cursor**：`.cursor/rules/*.mdc` 里 `alwaysApply:true` 的规则会常驻每一次请求——常驻既吃 token，也意味着你一改它就动了前缀（来源：[Cursor Docs](https://cursor.com/docs)）。

行动项：**别在 session 中途改 `CLAUDE.md` / `AGENTS.md` / Rules。** 要改，改完再开新会话。这一招不改变输出质量，只改变你的账单——但幅度是 200 倍。

## 六、Claude Code 用户的每回合 5 选项（压缩版）

如果你主力是 Claude Code，前面所有原理最后会落到一个具体的肌肉记忆上：**每次 Claude 回完话，都是一个分叉点，你有五个选项，而大多数人只会用第一个。**

| 选项 | 什么时候用 |
|------|-----------|
| **continue（继续）** | 顺着往下做，最常用也最被滥用 |
| **rewind（`esc esc`）** | 上一次尝试失败——回退到尝试之前重新提问，而不是留着失败记录继续纠正 |
| **`/compact`** | 完成一个任务、或窗口约半满时主动压缩（加方向） |
| **`/clear`** | 换一件无关的活——写好 brief，清空重启，换干净前缀 |
| **subagent** | 这一步的中间输出你不想要，只要结论 |

其中最能体现「上下文管理水平」的一个习惯是 **rewind**：与其对模型说「刚才那个不行，试试 X」（失败尝试会留在窗口里污染后续），不如回退到失败之前、带着教训重新提问（来源：[Thariq，《Using Claude Code: Session Management & 1M Context》，2026-04-16](https://x.com/trq212/status/2044548257058328723)）。

> 这五个选项的逐条展开、以及它们背后的「每回合停 2 秒」决策框架，我们另有一篇专文详述，这里只做索引，不重复铺开。

## 七、收尾：换工具，不用重学

把三家放回一张表，本文的论点就自证了——它们不是三套要分别背诵的技巧，而是**同一门手艺的三种方言**：

| 你要做的事 | Claude Code | Codex | Cursor |
|-----------|-------------|-------|--------|
| 浓缩长历史 | `/compact` + 自动微压缩 | 自动压缩（`encrypted_content`） | 开新 chat |
| 丢掉失败尝试 | `/rewind` | 开新 thread | 开新 chat |
| 隔离中间过程 | subagent | —— | Skills 动态加载 |
| 省钱（护缓存） | 前缀稳定 | 别改 `AGENTS.md` | 慎用常驻 Rules |

看穿这张表，你迁移的是**判断力**，不是快捷键。快捷键会随工具变，判断力——「这一步该留、该丢、还是该隔离？」——三家通用。

**下一步往哪走？**
- 想把上面这套「运行时窗口怎么管」升级成「持久上下文怎么组织」（Identity / Audience / Standards / Project 四个常驻文件），可以往 context engineering 的方向深挖（来源：[Khairallah，《How to master context engineering》](https://x.com/eng_khairallah1/status/2053405155630936297)）。
- 想读一份把「入门骨架」讲得最系统的长文，Anthropic 那篇《Effective context engineering》值得逐段精读——本文的分层结构就受它影响。

上下文管理这门手艺，学一次，三家都能用。
