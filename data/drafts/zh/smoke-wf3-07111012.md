# 约束解码 vs 校验重试:让 LLM 稳定吐 JSON 的两层心智模型 + 一份失败模式清单

**一句话价值**:让 LLM 稳定输出结构化 JSON,不是「把 prompt 写得更客气一点」,而是一个两层工程问题——生成期用**约束解码(constrained decoding)**保证格式一定合法,事后用**校验器(validator)**保证值也对。看穿这两层,你就不会再被「strict 模式=绝对保证」这句半真半假的话骗到。

**谁该读**:会调 OpenAI / Anthropic / Gemini 的 API、能跑通脚本,但不是 systems engineer 的 AI builder。你不需要懂 token mask 的底层实现,只需要知道「哪层保什么、哪层会漏、生产里我该在外面包什么」。深水区(约束解码的性能数据、alignment tax 的学术争议)放在后段,浅读者可以在任意小节停下。

> **本文的工作论点(编辑立场,非作者亲笔署名观点)**:市面上绝大多数「怎么让 LLM 吐 JSON」的教程,只教你调对一个 API 参数,停在「格式对了就万事大吉」。但真正能迁移的心智模型是两层——**生成期约束**(格式一定对)+ **事后校验**(值也得对、业务规则也得过)。而且被反复吹的「strict」根本不是黑箱式的绝对保证:它有 refusal、`max_tokens` 截断、schema 子集三条**静默泄漏**暗门。结构化输出是你**仍然要 verify** 的 deterministic guardrail(确定性护栏),不是可以盲信的自动挡。把这层看穿,你写的每一段 JSON 提取代码都会更抗造。

---

## 一、先纠正一个起点错误:吐 JSON 不是「求模型配合」

**定义先行**:结构化 JSON 输出 = 让 LLM 产出**能被程序直接解析、且符合预定义 schema** 的 JSON,而不是在一段自由文本里夹一块可能格式错的 JSON。

很多人对这件事的心智还停在 2023 年的「JSON mode」:在 prompt 里写「请只返回 JSON,不要解释」,然后祈祷模型听话。这个认知已经过时。现在主流供应商的严格模式,底层是**约束解码**——在每一步生成时,系统会算出一个只包含「此刻符合 schema 的合法 token」的掩码(mask),模型**物理上吐不出**违反 schema 的 token。这不是求配合,是把格式约束焊死在采样层。

差距有多大?OpenAI 在发布 Structured Outputs 时给了一个可核验的数字:在它内部的 schema-following 评测里,`gpt-4o-2024-08-06` 配合结构化输出达到 **100%**,而老模型只有 **~40%**(来源:[OpenAI,《Introducing Structured Outputs in the API》,2024-08-06](https://openai.com/index/introducing-structured-outputs-in-the-api/))。从「~40% 靠祈祷」到「100% 靠采样层保证」,这就是「求配合」和「工程保证」的分野。

记住这一句,后面全篇都是它的展开:**格式合法这件事,早就该从 prompt 层下沉到解码层。**

## 二、两层心智模型:格式对 ≠ 值对(本文骨架)

把整个领域装进脑子,只需要一张两层图:

**第一层——生成期保证(约束解码)**:解决「**格式一定对**」。约束解码在采样时压 token mask,产出的 JSON 一定能被 `json.loads` 解析、一定符合 schema 的结构。代表:三家供应商原生 Structured Outputs、开源的 Outlines / llguidance。

**第二层——事后校验(validation)**:解决「**值也得对**」。约束解码保证不了业务语义——它能保证 `age` 字段是整数,保证不了这个整数 `>= 0`;能保证 `email` 是字符串,保证不了它真的是邮箱格式,更保证不了「订单金额 = 单价 × 数量」这种跨字段规则。这一层用 Pydantic / Zod / JSON Schema validator 校验,**失败就把错误回灌进对话重问**(validate-and-reask)。代表:Instructor、Pydantic AI。

这两层的关键点——也是最容易被教程漏掉的一点——是**它们不互斥,而且常常叠用**:约束解码保 JSON 合法,校验器保语义和范围。Instructor 作者 Jason Liu 的 validate-and-reask 范式(Pydantic 校验失败→把校验错误塞回对话→让模型带着错误信息重答)被 OpenAI 官方点名为 Structured Outputs 的灵感来源;这个库月下载量已达 **~600 万**(来源:[Instructor 官方文档,reask & validation](https://python.useinstructor.com/concepts/reask_validation/);[OpenAI 公告同上](https://openai.com/index/introducing-structured-outputs-in-the-api/))。

用我们 vault 的老话说:这正是**「把 latent(潜在、不确定)的模型输出焊上 deterministic(确定性)护栏」**的具体工程落地——第一层焊格式,第二层焊语义。

## 三、三条技术路线对比表:什么时候用哪条

落到工具选择,今天有三条互不相同的技术路线,别混为一谈。下面这张表是本文最该收藏的一屏:

| 路线 | 代表 | 机制 | 什么时候用 | 出处 |
|------|------|------|-----------|------|
| **(a) 供应商原生 SO** | OpenAI `strict:true` / Anthropic `output_config.format` / Gemini `responseSchema` | 供应商在自家推理层做约束解码 | 简单抽取、不想自己维护基础设施 | [OpenAI docs](https://developers.openai.com/api/docs/guides/structured-outputs) · [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) · [Gemini docs](https://ai.google.dev/gemini-api/docs/structured-output) |
| **(b) 开源约束解码引擎** | Outlines / llguidance / XGrammar | 自己在推理层压 token mask,跨 vLLM/TGI/SGLang/Ollama | 自托管、换 backend、要极致性能 | [Outlines](https://github.com/dottxt-ai/outlines) · [llguidance](https://github.com/guidance-ai/llguidance) |
| **(c) 应用层校验+重问库** | Instructor / BAML / Pydantic AI | 事后 Pydantic 校验,失败回灌错误重试 | 需业务规则、跨字段校验、自愈 | [Instructor](https://github.com/567-labs/instructor) · [Pydantic AI](https://pydantic.dev/docs/ai/core-concepts/output/) |

读表的方式:**(a) 和 (b) 都在第一层(格式保证),(c) 在第二层(语义校验)**。它们不是三选一,而是常常 (a)+(c) 或 (b)+(c) 叠用——供应商原生保格式,应用层库保业务规则。只有当你既不自托管、需求又只是「把几个字段抽出来」时,才可能单用 (a) 就够。

一个入门读者常踩的坑:以为选了 (c) 的 Instructor 就不用管供应商的原生能力了。恰恰相反——Instructor 底层会优先调用供应商的原生 Structured Outputs 来保第一层,自己专注做第二层的校验循环。两层是协作,不是替代。

## 四、纠正一个正在过时的叙事:Anthropic 不再只能靠 forced tool use

如果你读的教程是 2024 或 2025 年初写的,大概率会看到这句话:「**Anthropic 没有原生结构化输出,只能靠 forced tool use(强制工具调用)绕**」。

**这句话现在是错的。** Anthropic 已经原生 GA 了独立于 tool use 的结构化输出特性 `output_config.format`,底层同样由约束解码支撑,覆盖 Opus / Sonnet / Haiku 4.x 以及 Fable / Mythos 5(来源:[Anthropic,Structured outputs 官方文档](https://platform.claude.com/docs/en/build-with-claude/structured-outputs))。工具作者 Simon Willison 也在 2025-11 更新了自己的 `llm-anthropic` 插件来对接这个新原生特性,算是一个交叉佐证(来源:[Simon Willison on X](https://x.com/simonw/status/1989800630416990475))。

> [!warning] 矛盾留档:两个 claim 都记下,写代码用新的
> **旧叙事(❌ 已过时)**:Anthropic 只能 forced tool use、无原生结构化输出、无字段级流式。
> **新事实(✅ 已核验)**:`output_config.format` 是独立于 tool use 的原生特性,已 GA。
> 为什么值得单独标出来:这类「能力已经变了、认知还没跟上」的错配,是你今天读到的第三方教程里最常见的过期知识点。凡涉及供应商能力,**回一手官方文档核对日期**,别信二手教程的断言。

## 五、失败模式清单:「strict」是有条件的保证,不是黑箱

这是全网教程最普遍缺的一节,也是本文最贴我们立场的一节。**「strict」不等于「绝对保证」**——它有三条静默泄漏(silent leak)暗门,每一条都可能让「严格模式」返回不合 schema 的东西:

> [!warning] strict 模式的三条静默泄漏暗门
> **① 安全拒答(refusal)**:模型出于安全策略拒绝回答时,返回的是一个 refusal,而不是你 schema 里那个对象。约束解码管不到这条——拒答发生在更前面。
> **② `max_tokens` 截断**:如果生成被 token 上限打断,你会拿到一段**语法上残缺**的 JSON(少个 `}`、字符串没闭合)。格式保证在这里失效,因为它根本没生成完。Simon Willison 反复提示:output-token 上限才是那个真正的隐形约束。
> **③ schema 子集限制**:各家的「strict」只支持 JSON Schema 的一个**子集**。以 Anthropic 为例:不支持递归 schema、不支持数值约束(min/max)、不支持字符串长度、不支持 lookahead regex;上限 20 个 strict tools、24 个可选参数、16 个 union 参数。OpenAI 则强制 `additionalProperties:false` + 所有属性进 `required`,且首次请求有 schema 编译延迟。你写的约束若落在子集之外,要么被静默忽略,要么请求期直接被拒。
> 出处:[OpenAI docs](https://developers.openai.com/api/docs/guides/structured-outputs) · [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

这三条合起来,就是我们 vault 里 **silent-fallback(静默降级)反模式** 的活体标本:系统看起来「成功」返回了,实际上悄悄降级了,而你的代码如果不检查,就会把一段残缺 JSON 当合法数据往下传。

**行动项**:任何路线,都要在 schema 之外再包一层**显式校验 + 失败硬停或有上限重试**。把 refusal 和截断当**一等公民**处理——单独判断、单独报错,**禁止静默吞掉**。结构化输出是护栏,不是免检通行证。

## 六、两则反直觉:约束解码更快,但可能税掉推理质量

处理完「会漏」,再处理两个反常识点,分别服务两种深读者。

**反直觉一(站得住):约束解码常常更快,不是更慢。** 直觉里「加约束=加负担=更慢」,但事实相反:约束把每一步的候选 token 变少了,采样反而更快。llguidance 的运行时即时算 mask 已经做到 **~6–9ms/token,低于无约束基线**;JSONSchemaBench(~10k 真实 schema × 6 框架)也从经验上支持「约束解码可以快于无约束」这个结论(来源:[llguidance repo](https://github.com/guidance-ai/llguidance);[JSONSchemaBench, arXiv 2501.10868](https://arxiv.org/pdf/2501.10868))。「约束=更慢」是过时印象。

**反直觉二(有争议,两面写):强压 grammar 可能税掉推理质量。** 这一条要诚实标注:多篇 2025–2026 的论文报告,约束解码 / 强制 grammar 在**推理、反思类任务**上可能降低语义正确性,被称作 "alignment tax"(对齐税)(来源:[arXiv 2604.06066](https://arxiv.org/pdf/2604.06066))。

> [!note] 这是研究阶段结论,不是普适定论
> alignment tax 是**任务相关**的,目前处于 contested(有争议)状态,不能当成「约束解码一定伤智商」的铁律。但它给了一个可操作的推论:**约束保证格式对 ≠ 保证内容对**。对需要「先想清楚再回答」的任务,别一上来就锁死 grammar——考虑先让模型自由推理,再把结论做二次结构化;或者用容错解析器(如 BAML)留一点余地。

两条放一起的教训:性能上你可以放心用约束解码;但**质量上,格式合法从来不等于答案正确**——第二层的语义校验永远不能省。

## 七、落地清单:按四场景选路线,任何路线都外包一层校验

把全文压成一张「照着做」的决策表。先问自己是哪种场景:

| 你的场景 | 选哪条路线 | 为什么 |
|---------|-----------|--------|
| **简单抽取**(把几个字段抽出来) | 供应商原生 SO(`strict:true` / `output_config.format` / `responseSchema`) | 第一层足够,别过度工程 |
| **业务规则 / 跨字段校验 / 要自愈** | 叠 Instructor 或 Pydantic AI | 需要第二层的 validate-and-reask 循环 |
| **自托管 / 换 backend / 要极致性能** | Outlines 或 llguidance | 自己掌控约束解码层,llguidance 近零启动 |
| **需要推理质量的任务** | 先自由推理,再二次结构化;或用 BAML 容错解析 | 规避 alignment tax,别一上来锁 grammar |

无论你落在哪一格,有**一条纪律对所有路线通用**:**在 schema 之外再包一层显式校验 + 失败硬停或有上限重试**,把 refusal / 截断当一等公民,禁止静默降级。这是把结构化输出当「确定性护栏」而非「黑箱」的唯一正确姿势。

**角色化收尾——如果你是……**
- **独立 builder**:先别自建约束解码基础设施。用供应商原生 SO 打底(第一层),需要业务规则时叠 Instructor(第二层),两行代码起步,够用再升级。
- **内容创作者 / 做提取管线的**:你最该防的是第五节那三条暗门——批量提取时一段截断的 JSON 会静默污染整批数据。在管线里加一道显式校验闸,失败进死信队列,别静默丢。
- **团队 lead**:把「结构化输出必须外包一层校验 + 硬停」写进你们的 code review 清单;把「供应商能力回一手文档核对」写进纪律——本文第四节那种过期认知,是团队里最贵的隐性债。

一句话收尾:**约束解码保证你拿到的是合法 JSON,校验器保证你拿到的是对的 JSON,而只有你自己的硬停逻辑,保证一段悄悄降级的输出不会被当成成功。** 这三层,一层都不能省。
