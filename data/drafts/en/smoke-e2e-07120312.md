# Why You Can't Let AI Be the Only Reviewer of AI-Written Code

This year, Anthropic says code output per engineer is up **+200%** ([Boris Cherny, first-hand](https://x.com/bcherny/status/2031089411820228645)). The creator of Claude Code went two straight months writing 100% of his code with AI — zero hand edits, 20-plus PRs a day. Writing code is getting cheaper by the week.

So the bottleneck moved. It's no longer "who types the code out" — it's "who reviews the flood of it." Anthropic's answer: dispatch **a team of agents** to hunt bugs on every PR in parallel, then add a verification step to filter false positives (official line: engineers flag fewer than 1% of findings as wrong — [Anthropic Code Review](https://claude.com/blog/code-review)). Cursor's BugBot handles 2M PRs a month and pushes `/review` forward into a pre-push gate ([Cursor BugBot](https://cursor.com/bugbot)). "Dispatch a squad of AI to review every PR" is becoming the 2026 default move.

**But there's a swap hiding in here: if the thing writing the code and the thing reviewing it are the same kind of AI, did anyone actually understand this code?**

That's the take of this piece. In the AI-pairing era, writing code got cheap — so the real moat is whether *anyone rebuilt the intent* behind a change. A **single-model closed loop** — AI writes, the same kind of AI reviews, it passes — quietly swaps "the system is actually correct" for "you *assume* it's correct." The review goes green, but no independent perspective ever reconstructed the intent. The way out isn't a stronger single model; it's **heterogeneous multi-model review + a human *on* the loop, sampling deeply.** Here's the unpack.

## 1. Turn the default move into a question

A clean definition first. **Code review in the AI-pairing era** is this: once AI agents write most of the code, the human's focus shifts from "checking the author's mechanical correctness" to "rebuilding the author's missing intent + guarding architecture, security, and system knowledge" — while the mechanical layer (formatting, lint, common bugs) gets outsourced to dedicated AI review agents.

Simon Willison puts it more bluntly. He cites Strong DM's two rules — "code must not be written by a human / code must not be reviewed by a human" — then asks: when half your code is agent-written, what are you even reviewing? He names the condition **"cognitive debt"**: you *own* a pile of code that neither you nor anyone else ever actually understood ([Simon Willison](https://x.com/simonw/status/2020161285376082326)).

Cognitive debt doesn't blow up right away. It blows up three months later, when a module nobody ever rebuilt the intent for fails — and the thing that "reviewed" it back then was just another AI.

## 2. Name the trap: borrowed confidence

This section is the crux; the term has to hold.

The most expensive failure mode of closed-loop self-review **is not a missed bug**. A missed bug still has a next line of defense. The most expensive one is what Addy Osmani named **"borrowed confidence"**: AI generates the code, another AI reviews and approves it, the whole chain looks fine — green all the way — and so "the system is definitely correct" gets silently swapped for "*you feel* it's correct." That confidence was borrowed from a machine. Nobody checked the books ([Addy Osmani, Agentic Code Review](https://addyosmani.com/blog/agentic-code-review/)).

It's the most hidden failure precisely because it looks the most normal. A missed bug throws an error. Borrowed confidence doesn't — it ships a smooth, green, unaccountable sense of certainty.

And same-source models have **correlated** blind spots. Osmani cites a study: run 4 AI review tools in parallel, and **93.4% of bugs were caught by only one of them** (⚠️ Osmani's second-hand citation; original study link pending — treat as reported, not verified first-hand). Put differently: if you run one tool, or a pile of same-source, same-architecture tools, you *think* you're doing "multiple reviews" — but they're most likely blind in the same spot, together. Greptile calls this the second-order effect: the first-layer problem (can it catch real bugs) is mostly solved; **the correlated blind spots of AI-reviewing-AI are the real battleground** ([Greptile](https://www.greptile.com/blog/ai-code-reviews-conflict)).

## 3. Why self-review bias is inevitable (the mechanism)

Third-party research can hand you the phenomenon. This section hands you what they can't: *why* heterogeneous review works, and *why* self-review is necessarily biased.

The first mechanism is **self-evaluation bias**. Ask an agent to judge its own output and it will **over-confidently approve its own mediocre work** — because "generate" and "judge" share the same priors: the failure modes it didn't think of while generating are the same ones it can't see while judging. The blind spot is one blind spot. That's the mechanistic explanation of borrowed confidence: self-review isn't a *bias* problem, it's an *information-structure* problem — judge and author are the same information source, and no amount of confidence lights up your own backside.

The second mechanism explains *why* heterogeneous review rescues you: it works **not by majority vote, but by three complementary axes**. Hand the same output to models from different vendors with different strengths — one skewed toward **precision** (few false positives), one toward **recall** (catches more real issues), one toward **genericness** (flags the say-nothing boilerplate). Each axis lights up one face; together they approximate the whole. This is nothing like "three identical models voting" — three same-source models just vote the same blind spot three times.

So "4 tools, 93.4% of bugs caught by only one" is, mechanistically, **inevitable, not accidental**: each tool is one axis, and there *should* be little overlap between axes. Low overlap isn't a bug — it's the evidence that heterogeneity is working. The value of heterogeneous review lives exactly inside the bugs "only one tool caught."

## 4. The prescription: how to build blind-spot-resistant review

Translate the mechanism into an executable structure — three parts:

**1. Run heterogeneous models in parallel.** Different vendors, different strengths, reviewing the same PR at once, covering the precision / recall / genericness axes. The load-bearing word is *heterogeneous* — two tools from different sources beat one "strongest" tool.

**2. A coordinator to dedupe and rank.** Multiple reviewers produce overlap and noise; you need a layer to dedupe findings, rank by severity, and emit a high-signal overview. Cloudflare runs up to **7 specialized reviewers** in production (security / performance / quality / docs / release / compliance / internal Codex) behind a coordinator that dedupes and ranks ([Cloudflare](https://blog.cloudflare.com/ai-code-review/)). You don't need 7 — but you need that coordinator layer, or heterogeneous review drowns in its own noise.

**3. A human *on* the loop, not *in* it.** This is where Osmani's line lands: the human no longer reads line by line (*in* the loop), nor hands everything to AI self-review (*off* the loop) — the human sits **on** the loop and samples deeply, spot-checking intent reconstruction, architecture decisions, and security exposure — the judgment machines can't backfill. Outsource the mechanical layer (formatting, lint, common bugs, security patterns) entirely; the human doesn't glance at it. Keep the judgment layer (architecture, public-API ergonomics, algorithm choice, dependency/security exposure, business logic, testability) for the human to dig into, sampled.

> One-line mnemonic: **outsource mechanical review entirely; never outsource intent review.**

## 5. A shipping checklist: the minimum viable version for a non-senior builder

If you're an **independent builder or content creator** — you use Claude Code / Cursor / API, you can run scripts, but you're not a systems engineer — you don't need Cloudflare's 7-reviewer orchestration. The smallest blind-spot-resistant stack you can wire up today:

1. **Run two tools from two different vendors in parallel.** Not one, not a same-source pile — *two different sources*. That single step already fights correlated blind spots, at near-zero config cost.
2. **Move review forward into a pre-push gate.** Hang `/review` before push, not at the PR stage. Pre-push is the cheapest place to catch a bug — the later you find it, the more it costs ([Cursor BugBot](https://cursor.com/bugbot)).
3. **One human sample, refusing source bias.** Pull a subset of each batch and rebuild the intent by hand. When you review, **don't ask "was this written by a senior engineer or an agent" — only ask "does it run, is it safe."** Code is disposable; system knowledge is permanent ([Daniela Petruzalek](https://danicat.dev/posts/20260303-code-reviews-in-2026/)).
4. **Force a linear walkthrough on high-risk changes.** For auth, payments, data migrations — don't sample. Trace the logic line by line and keep cognitive debt out.

This costs far less than chasing one "strongest single model," and resists blind spots far better. Because **the value of review was never in catching mechanical bugs** — hand those to a machine, it's cheapest there — **its value is this: forcing at least one independent perspective (a human, or a genuinely heterogeneous model) to re-understand the change.**

Writing code got cheap. Understanding didn't. The moat sits in that seam that never got cheap.
