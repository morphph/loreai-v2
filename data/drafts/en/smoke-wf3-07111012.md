# Constrained Decoding vs. Validate-and-Retry: The Two-Layer Mental Model for Getting Reliable JSON out of an LLM (plus a failure-mode checklist)

**The one-line value**: Getting an LLM to emit structured JSON reliably is not about writing a politer prompt. It's a two-layer engineering problem — use **constrained decoding** at generation time so the format is always valid, then use a **validator** afterward so the values are correct too. Once you see both layers, the half-true claim that "strict mode = a guarantee" stops fooling you.

**Who should read this**: AI builders who call the OpenAI / Anthropic / Gemini APIs and can ship a script, but aren't systems engineers. You don't need to understand how token masks are implemented — you need to know which layer guarantees what, where it silently leaks, and what you must wrap around it in production. The deep end (constrained-decoding latency numbers, the alignment-tax debate) sits in the back half; skim-readers can stop at any section.

> **The working thesis of this piece (an editorial stance, not the author's personally-signed take)**: Almost every "how to get JSON out of an LLM" tutorial teaches you to set one API parameter correctly and stops at "the format parsed, so we're done." But the mental model that actually transfers is two layers — **generation-time constraint** (format is always valid) plus **post-hoc validation** (the values must be right, and the business rules must pass). And the much-hyped "strict" mode is not a black-box absolute guarantee: it has three **silent leak** doors — refusal, `max_tokens` truncation, and the schema subset. Structured output is a **deterministic guardrail you still have to verify**, not an automatic transmission you can trust blindly. See both layers and every JSON-extraction path you write gets sturdier.

## 1. Fix the starting mistake: emitting JSON is not "asking the model nicely"

**Definition first**: Structured JSON output means getting an LLM to produce JSON that a program can parse directly **and** that conforms to a predefined schema — not a block of possibly-malformed JSON buried in free text.

Most people's mental model here is still stuck in 2023-era "JSON mode": write "return only JSON, no explanation" in the prompt and pray the model complies. That's outdated. The strict modes shipped by today's major providers are backed by **constrained decoding**: at every generation step, the system computes a mask containing only the tokens that are *legal under the schema at that moment*, so the model is **physically unable** to emit a schema-violating token. This isn't asking for cooperation — it's welding the format constraint onto the sampling layer.

How big is the gap? When OpenAI launched Structured Outputs it gave a checkable number: on its internal schema-following eval, `gpt-4o-2024-08-06` with structured outputs hit **100%**, versus **~40%** for older models (source: [OpenAI, "Introducing Structured Outputs in the API," 2024-08-06](https://openai.com/index/introducing-structured-outputs-in-the-api/)). From "~40% and pray" to "100% guaranteed at the sampling layer" — that's the line between "asking nicely" and "engineering a guarantee."

Keep one sentence in mind; the rest of the piece unpacks it: **legal format should have moved out of the prompt layer and down into the decoding layer long ago.**

## 2. The two-layer mental model: valid format ≠ correct values (the skeleton of this piece)

You can fit the whole field in your head with one two-layer diagram:

**Layer 1 — generation-time guarantee (constrained decoding)**: solves "**the format is always valid**." Constrained decoding applies a token mask during sampling, so the JSON that comes out is always parseable by `json.loads` and always conforms to the schema's structure. Representatives: the three providers' native Structured Outputs; open-source Outlines / llguidance.

**Layer 2 — post-hoc validation**: solves "**the values must be correct too**." Constrained decoding can't guarantee business semantics — it can guarantee `age` is an integer, but not that the integer is `>= 0`; it can guarantee `email` is a string, but not that it's a real email, let alone a cross-field rule like "order total = unit price × quantity." This layer validates with Pydantic / Zod / a JSON Schema validator and, **on failure, feeds the error back into the conversation and re-asks** (validate-and-reask). Representatives: Instructor, Pydantic AI.

The key point about these two layers — the one tutorials most often drop — is that **they aren't mutually exclusive; they're usually stacked**: constrained decoding keeps the JSON legal, the validator keeps the semantics and ranges honest. Instructor author Jason Liu's validate-and-reask pattern (Pydantic validation fails → the validation error is pushed back into the conversation → the model re-answers carrying that error) was named by OpenAI as an inspiration for Structured Outputs; the library now sees **~6M monthly downloads** (sources: [Instructor docs, reask & validation](https://python.useinstructor.com/concepts/reask_validation/); [OpenAI announcement, ibid.](https://openai.com/index/introducing-structured-outputs-in-the-api/)).

In our vault's terms, this is the concrete engineering instance of **welding a deterministic guardrail onto a latent (uncertain) model output** — layer 1 welds the format, layer 2 welds the semantics.

## 3. The three-route comparison table: when to use which

Down at the tool-choice level, there are three distinct technical routes today. Don't conflate them. The table below is the one screen worth saving:

| Route | Representatives | Mechanism | When to use | Source |
|-------|-----------------|-----------|-------------|--------|
| **(a) Provider-native SO** | OpenAI `strict:true` / Anthropic `output_config.format` / Gemini `responseSchema` | Provider does constrained decoding in its own inference layer | Simple extraction; you don't want to run infra | [OpenAI docs](https://developers.openai.com/api/docs/guides/structured-outputs) · [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) · [Gemini docs](https://ai.google.dev/gemini-api/docs/structured-output) |
| **(b) Open-source constrained-decoding engines** | Outlines / llguidance / XGrammar | You apply the token mask at the inference layer, across vLLM/TGI/SGLang/Ollama | Self-hosting, swapping backends, squeezing performance | [Outlines](https://github.com/dottxt-ai/outlines) · [llguidance](https://github.com/guidance-ai/llguidance) |
| **(c) App-layer validate-and-retry libraries** | Instructor / BAML / Pydantic AI | Post-hoc Pydantic validation; on failure, feed error back and retry | Business rules, cross-field validation, self-healing | [Instructor](https://github.com/567-labs/instructor) · [Pydantic AI](https://pydantic.dev/docs/ai/core-concepts/output/) |

How to read the table: **(a) and (b) both live in layer 1 (format guarantee), (c) lives in layer 2 (semantic validation)**. They aren't one-of-three; they're often stacked (a)+(c) or (b)+(c) — provider-native keeps the format legal, the app layer keeps the business rules. Only when you're not self-hosting *and* your need is just "pull a few fields out" might route (a) alone be enough.

A common beginner trap: assuming that picking Instructor (route c) means you can ignore the provider's native capability. It's the opposite — under the hood Instructor prefers to call the provider's native Structured Outputs to cover layer 1, and focuses its own effort on the layer-2 validation loop. The two layers collaborate; they don't replace each other.

## 4. Correct an narrative that's going stale: Anthropic no longer needs forced tool use

If the tutorial you read was written in 2024 or early 2025, it probably says: "**Anthropic has no native structured output; you have to work around it with forced tool use.**"

## 5. The failure-mode checklist: "strict" is a conditional guarantee, not a black box

This is the section almost every tutorial online is missing, and the one closest to our stance. **"strict" does not equal "an absolute guarantee"** — it has three silent-leak doors, each of which can make "strict mode" return something that doesn't match the schema:

> [!warning] The three silent-leak doors of strict mode
> **① Safety refusal**: when the model declines on a safety policy, it returns a refusal, not the object in your schema. Constrained decoding can't reach this — the refusal happens upstream of it.
> **② `max_tokens` truncation**: if generation is cut off by the token limit, you get **syntactically incomplete** JSON (a missing `}`, an unterminated string). The format guarantee fails here because it never finished generating. Simon Willison keeps pointing out that the output-token limit is the real invisible constraint.
> **③ Schema-subset limits**: each provider's "strict" supports only a **subset** of JSON Schema. Anthropic, for example: no recursive schemas, no numeric constraints (min/max), no string-length constraints, no lookahead regex; caps of 20 strict tools, 24 optional params, 16 union params. OpenAI forces `additionalProperties:false` + all properties into `required`, and adds schema-compilation latency on the first request. Any constraint you write that falls outside the subset is either silently ignored or rejected at request time.
> Sources: [OpenAI docs](https://developers.openai.com/api/docs/guides/structured-outputs) · [Anthropic docs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)

Put together, these three are a live specimen of our vault's **silent-fallback anti-pattern**: the system looks like it "succeeded," but it quietly degraded — and if your code doesn't check, it passes a mangled chunk of JSON downstream as valid data.

**Action item**: on any route, wrap an **explicit validation + hard-stop or bounded retry** layer around the schema. Treat refusal and truncation as **first-class citizens** — check for them, raise on them, and **never swallow them silently**. Structured output is a guardrail, not an inspection-free pass.

## 6. Two counter-intuitive facts: constrained decoding is faster, but may tax reasoning quality

Having handled "it leaks," handle two counter-intuitive points, each for a different deep reader.

**Counter-intuition one (holds up): constrained decoding is often faster, not slower.** Intuition says "add constraints → add overhead → slower," but the reverse is true: constraints shrink the candidate-token set at each step, so sampling gets faster. llguidance's runtime just-in-time mask already hits **~6–9ms/token, below the unconstrained baseline**; JSONSchemaBench (~10k real schemas × 6 frameworks) also empirically supports the conclusion that constrained decoding can beat unconstrained (sources: [llguidance repo](https://github.com/guidance-ai/llguidance); [JSONSchemaBench, arXiv 2501.10868](https://arxiv.org/pdf/2501.10868)). "Constraints = slower" is an outdated impression.

**Counter-intuition two (contested, write both sides): forcing grammar may tax reasoning quality.** Flag this one honestly: several 2025–2026 papers report that constrained decoding / forced grammar may lower semantic correctness on **reasoning and reflection tasks** — an "alignment tax" (source: [arXiv 2604.06066](https://arxiv.org/pdf/2604.06066)).

> [!note] This is a research-stage finding, not a universal law
> The alignment tax is **task-dependent** and currently contested; don't take it as an iron rule that "constrained decoding always dumbs the model down." But it yields one actionable corollary: **a guaranteed format ≠ a correct content.** For tasks that need "think it through, then answer," don't lock the grammar from the first token — consider letting the model reason freely first, then do a second structuring pass on the conclusion; or use a fault-tolerant parser (like BAML) to leave some slack.

The lesson from both together: on performance, use constrained decoding with confidence; but on quality, **a legal format is never the same as a correct answer** — the layer-2 semantic validation can never be dropped.

## 7. The landing checklist: pick a route by four scenarios, and outsource a validation layer on every one

Compress the whole piece into one "just do this" decision table. First ask which scenario you're in:

| Your scenario | Which route | Why |
|---------------|-------------|-----|
| **Simple extraction** (pull a few fields out) | Provider-native SO (`strict:true` / `output_config.format` / `responseSchema`) | Layer 1 is enough; don't over-engineer |
| **Business rules / cross-field validation / self-healing** | Stack Instructor or Pydantic AI | You need the layer-2 validate-and-reask loop |
| **Self-hosting / swapping backends / max performance** | Outlines or llguidance | Own the constrained-decoding layer; llguidance is near-zero startup |
| **Reasoning-quality-sensitive tasks** | Reason freely first, then a second structuring pass; or BAML fault-tolerant parsing | Dodge the alignment tax; don't lock grammar from the start |

Whichever cell you land in, **one discipline is universal to every route**: wrap an **explicit validation + hard-stop or bounded retry** layer around the schema, treat refusal / truncation as first-class citizens, and forbid silent degradation. That's the only correct posture for treating structured output as a "deterministic guardrail" rather than a "black box."

**Role-based close — if you are…**
- **An independent builder**: don't build constrained-decoding infra yourself. Start with provider-native SO for the floor (layer 1), stack Instructor when you need business rules (layer 2) — two lines to start, upgrade when you outgrow it.
- **A content creator / running an extraction pipeline**: the thing to defend against most is the three doors in Section 5 — in bulk extraction, one truncated chunk of JSON silently corrupts the whole batch. Add an explicit validation gate in the pipeline; failures go to a dead-letter queue, never dropped silently.
- **A team lead**: put "structured output must wrap a validation + hard-stop layer" on your code-review checklist; put "verify provider capabilities against first-party docs" into your discipline — the kind of stale knowledge in Section 4 is the most expensive hidden debt on a team.

One sentence to close: **constrained decoding guarantees you get legal JSON, the validator guarantees you get correct JSON, and only your own hard-stop logic guarantees that a quietly-degraded output doesn't get counted as a success.** All three layers — you can't skip any of them.
