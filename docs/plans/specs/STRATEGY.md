# LoreAI Unified SEO/AEO Strategy

> Authoritative strategic + tactical foundation for the LoreAI flagship-topic engine.
> Supersedes: `Part I — Strategy.md` (ChatGPT) and `aeo-seo-by-claude.md` (Claude).
> Implementation details live in SPEC-00 through SPEC-15.

---

## 1. Executive Thesis

LoreAI should evolve from a **newsletter-led publishing system** into a **flagship-topic-led topic graph system**.

The current system is strong at collecting information and producing daily content, but its long-term SEO/AEO potential is constrained because:

- SEO assets are structurally downstream of newsletter and blog selection.
- FAQ and compare generation have been starved relative to glossary generation.
- No topic currently has complete cluster coverage.
- Technical SEO issues are suppressing discoverability even when content quality is strong.

The recommended strategic move is to:

1. **Demote newsletter from the main SEO gatekeeper to a downstream distribution layer.**
2. **Promote topic graph planning to the center of the content system.**
3. **Use Claude Code as the first flagship topic template.**
4. **Use Codex as the second flagship topic after the Claude Code template is proven.**
5. **Run English as the primary authority layer and Chinese as a selective localized growth layer.**

The long-term goal is not "publish more content." It is to build a reusable system that can continuously:

- absorb raw signals,
- detect topic graph gaps,
- generate the right asset types,
- connect them into a coherent cluster,
- refresh them as the market changes,
- and compound SEO/AEO traffic over time.

## 2. Diagnosis

### 2.1 What LoreAI is already doing well

- High-volume multi-source ingestion
- A working daily publishing pipeline
- Multilingual publishing capability
- An emerging topic and keyword data layer
- Meaningful early Claude Code coverage
- Enough raw material to support a graph-led system

The problem is **not lack of content input**. The problem is that the output system is not yet optimized for flagship-topic authority.

### 2.2 Core bottlenecks

#### A — Serial dependency chain

Current flow is: **Collect → Newsletter → Blog → SEO**

This causes downstream starvation. If newsletter selection is narrow, or blog seed generation is narrow, then FAQ, compare, and topic assets are constrained even when the raw signal layer is rich.

#### B — Wrong production unit

LoreAI is still implicitly optimizing around "daily content production" rather than **topic cluster completeness**. The correct production unit for long-term SEO/AEO is one flagship topic cluster, made up of multiple coordinated asset types, with explicit internal linking and refresh logic.

#### C — Cluster imbalance

The existing system overproduces glossary pages relative to FAQ, compare, and topic hubs. That creates breadth without enough search-intent capture.

#### D — Technical SEO suppression

Technical issues reduce the upside of existing content. These issues are foundational rather than cosmetic and must be resolved before aggressive scale-up.

#### E — Inconsistent source grounding

The cluster pipeline generates pages from real sources (official docs, competitor content). The daily pipeline generates the exact same content types from AI memory alone — risking hallucinated features and pricing. Same content type, two quality levels, depending on which entry point triggered generation.

#### F — No link validation / post-generation QA

The system tells the AI to add internal links but never verifies whether those links point to real pages. If the AI invents a link to `/glossary/some-term` and that page doesn't exist, a broken link gets published.

### 2.3 Strategic implication

LoreAI should stop treating SEO assets as blog byproducts and instead treat them as **first-class graph nodes** generated by a planner.

### 2.4 GSC evidence

GSC 90-day data confirms the bottlenecks are real:

- **4 total impressions** for "what is claude code" at position 60–75
- Claude Code topic hub: **zero impressions**
- Compare pages: **not ranking**
- 34 FAQ pages: 397 impressions, **zero clicks**
- Blog is the only content type generating clicks (GPT-5.3 Codex SWE-bench post: 1,732 impressions alone)
- The highest-impression page (1,772 impressions) is a **404** from old `/en/` URLs

Despite having 19 blog posts, a topic hub, and glossary entries for Claude Code, the site captures near-zero Claude Code search traffic.

## 3. North Star

> For each high-potential topic, LoreAI should become a clearly structured answer source across head terms, mid-funnel comparisons, long-tail FAQs, and concept definitions, with enough internal coherence that both search engines and LLMs can reliably understand, retrieve, and cite the site.

### 3.1 North-star outcomes

1. **Topic authority** — LoreAI becomes recognizably authoritative for a small set of target topics.

2. **Cluster completeness** — Each flagship topic has a coherent hub-spoke graph rather than isolated pages.

3. **Query coverage** — High-value informational, comparative, and definitional intents are systematically covered.

4. **AEO readiness** — Pages are structured to be extractable, quotable, and linkable in AI-generated answers:
   - **First-sentence-quotable answers:** FAQ and glossary content leads with a direct, extractable answer before elaboration.
   - **Feature tables for comparisons:** Compare pages use structured tables, not just prose — enabling AI systems to extract and cite specific feature differences.
   - **Schema types as structural requirements:** `FAQPage`, `DefinedTerm`, `Article`, and `BreadcrumbList` are not optional enhancements but mandatory structural signals for AEO.

5. **Compounding refreshability** — The system can detect when an existing node should be refreshed instead of creating endless new pages.

## 4. The Pipeline: 6-Stage Engine

The core principle of modern SEO is **topical authority** — you don't rank for individual keywords, you rank by proving comprehensive expertise on a topic cluster. The pipeline operationalizes this.

```
        ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
  ┌───────────┐    ┌───────────┐    ┌──────────┐   │
  │ 1. DETECT │───▶│ 2. MAP    │───▶│ 3. PLAN  │   │
  │  Topics   │    │  Cluster  │    │  Content │   │
  └───────────┘    └───────────┘    └────┬─────┘   │
                                         │         │
                                         ▼         │
                                   ┌──────────┐    │
                                   │ 4. CREATE │    │
                                   │  Content  │    │
                                   └────┬─────┘    │
                                        │         │
                                        ▼         │
                                   ┌──────────┐    │
                                   │ 5. LINK   │    │
                                   │ & VALIDATE│    │
                                   └────┬─────┘    │
                                        │         │
                                        ▼         │
                                   ┌──────────┐    │
                                   │ 6. MEASURE│────┘
                                   │ & REFRESH │  (feeds back)
                                   └──────────┘
```

Newsletter remains in the system as a consumer of the signal layer and the graph layer, not as the gatekeeper for SEO generation.

### 4.1 DETECT — Topic Discovery

**Question: "What should we write about?"**

- Monitor signals: official docs, changelogs, engineer blogs, GitHub activity, RSS, social discussion, videos and transcripts
- Identify **emerging topics before they peak**
- Output: candidate topics with demand signals — entities, compare pairs, question candidates, glossary candidates, freshness events, update triggers
- This is **entity/topic-level, not keyword-level**. "Claude Code" is a topic. "how to use claude code" is a keyword that belongs to it later.

**System role:** Signal engine (continuously ingests, normalizes, and outputs structured signals).

**Detection channels:**

| Channel | What It Catches | Frequency |
|---------|----------------|-----------|
| News pipeline (RSS, changelogs, blogs) | New features, launches, deprecations | Daily (automated) |
| GSC queries | User demand signals, ranking opportunities | Weekly import (automated) |
| SERP analysis (Serper.dev) | PAA boxes, related searches, competitor moves | Weekly (automated) |
| Semantic discovery (Exa) | "Unknown unknowns" — topics we didn't think to search for | Weekly (automated) |
| Community signals (Reddit, HN) | Real user questions, pain points, trending tools | Via news pipeline (automated) |
| Official documentation changes | New features, structural changes, API updates | Monthly structure scan (automated) + event-triggered |
| Human input | "I noticed X is trending" — manual topic injection | Anytime via `planner.ts --add-candidate` |

**Discovery cadence:**
- **Daily:** News pipeline entity extraction surfaces signals automatically.
- **Weekly:** Full discovery scan (Saturday) — SERP, Exa, GSC, competitor audit for all flagship clusters.
- **Monthly:** Official documentation structure diff for each flagship topic.
- **Event-triggered:** Major news (product launch, pricing change) triggers immediate discovery for affected clusters.
- **Manual:** Human can inject candidate topics anytime. Example: "Harness Engineering is trending" → add as candidate to the relevant cluster.

**Human notification (avoiding the blocker problem):**

The human should not need to poll for discovery results. The system surfaces candidates proactively:
- **Weekly discovery report** — generated alongside the Saturday cluster strategy run. Lists new high-scoring candidates, their signals, and recommended actions. Sent as a summary file + optionally as a notification.
- **Threshold-based auto-promotion** — candidates scoring above a configurable threshold (e.g., 80+) can be auto-promoted to the content queue without human approval, for low-risk content types (FAQ, glossary). High-investment types (cornerstone, deep-dive blog) always require human approval.
- **CLI dashboard** — `planner.ts --status` shows all pending candidates across clusters, sorted by score.

→ See: SPEC-09a (external discovery), SPEC-09c (internal signal discovery), SPEC-10 (GSC pipeline)

### 4.2 MAP — Cluster Definition

**Question: "How does this topic relate to others? What's the full topical map?"**

For each detected topic:
- **Step 0: Analyze official documentation structure** to seed the cluster map. The official docs define the topic's natural anatomy — features, workflows, integrations, pricing. This becomes the baseline. Example: Anthropic's Claude Code docs have sections for hooks, skills, agent teams, CLAUDE.md — each maps to a natural subtopic. Where official docs are thin (comparisons, real-world workflows, gotchas) is where LoreAI adds unique value.
  - **Scan frequency:** Monthly automated diff of official doc structure. Major version releases trigger immediate rescan.
  - **Rationale:** Official docs don't change daily, but when they do change, it often signals new cluster opportunities.
- Define the **pillar concept** (what are we the authority on?)
- Map **subtopics** and **related entities**
- Analyze the **SERP landscape** — what content types rank?
  - Featured snippets? → need FAQ pages
  - "vs" SERPs? → need comparison pages
  - PAA boxes? → need structured Q&A
  - Knowledge panels? → need entity-rich content
- Define **competitors** for this cluster (who ranks today?)
- Map search intent to content type:

| Search Intent | Content Type | Example |
|---|---|---|
| Informational | FAQ, How-to, Guide | "how does claude code work" |
| Commercial investigation | Compare, Alternatives | "claude code vs cursor" |
| Definitional | Glossary | "what is claude code" |
| Navigational | Cornerstone, Hub | "claude code" |

**System role:** Graph planner (part 1) — determines which topic is worth expanding and what node types are missing.

→ See: SPEC-03 (cluster definition), SPEC-09b (candidate management)

### 4.3 PLAN — Content Queue

**Question: "What specific pages do we need, in what order?"**

```
                    ┌─────────────────┐
                    │   CORNERSTONE   │  ← Comprehensive pillar page
                    │   (authority)    │     2000+ words, canonical
                    └───────┬─────────┘
            ┌───────────────┼───────────────┐
            ▼               ▼               ▼
     ┌────────────┐  ┌────────────┐  ┌────────────┐
     │ COMPARE    │  │ FAQ / Q&A  │  │ GLOSSARY   │
     │ (commercial│  │ (informa-  │  │ (defini-   │
     │  intent)   │  │  tional)   │  │  tional)   │
     └────────────┘  └────────────┘  └────────────┘
            │               │               │
            └───────────────┼───────────────┘
                            ▼
                    ┌─────────────────┐
                    │    TOPIC HUB    │  ← Navigation/linking page
                    │   (structure)    │     connects everything
                    └─────────────────┘
```

**Creation ordering matters:**
1. **Cornerstone first** — establishes authority
2. **Compare pages** — highest commercial intent
3. **FAQ pages** — captures long-tail + PAA boxes
4. **Glossary entries** — builds entity definitions for knowledge graphs
5. **Topic hub LAST** — needs content to exist before it can link to it

**Source grounding priority chain** (every factual page must be source-grounded):
1. Official documentation / primary sources
2. Competitor content analysis
3. News / recent developments
4. Community discussions (Reddit, HN — real user questions)

**System role:** Graph planner (part 2) — decides create vs. refresh, orders the asset queue.

→ See: SPEC-04 (cluster generation mode), SPEC-04b (source-grounded generation)

### 4.4 CREATE — Source-Grounded Content

**Question: "How do we create trustworthy, high-quality content?"**

**Every page should be source-grounded.** The quality difference between "AI writes from memory" and "AI writes from real sources" is massive for SEO — search engines increasingly detect thin/hallucinated content.

Source resolution by cluster tier:
- **Flagship clusters** → curated official URLs (best quality)
- **Auto clusters** → web search first, then use what we find (good quality)
- **Glossary and topic hubs** → no source needed (definitions and link pages)

**AEO micro-rules by content type:**

| Content Type | AEO Rule |
|---|---|
| FAQ | Answer in the first sentence, then elaborate. Structure for AI extraction. |
| Compare | Structured feature tables, not just prose. Lead with a clear verdict. |
| Glossary | One-sentence definition first. Precise, consistent entity mentions. |
| Cornerstone | Clear headings, direct answers at section tops. Comprehensive but scannable. |
| Deep-dive blog | Workflow-oriented. Code examples where relevant. |

**Production pipelines:**

LoreAI has two content production pipelines. The choice depends on depth and investment level:

| Pipeline | Trigger | Depth | Cost | Content Types |
|----------|---------|-------|------|---------------|
| **Standard SEO** (`generate-seo.ts`) | Automated from planner queue | 200–1,500 words | Low (single Claude call) | Compare, FAQ, Glossary, Topic Hub |
| **Daily blog** (`write-blog.ts`) | Automated from newsletter seeds | 800–1,500 words | Low (single Claude call) | Daily blog posts |
| **Deep-dive pipeline** (`write-topic-blog.ts`) | Manual or planner-triggered | 2,500–4,000 words | High (Gemini Deep Research + Claude subagents) | Deep-dive blog, Cornerstone |

**When to trigger which pipeline:**
- **Standard SEO:** Planner identifies a missing compare, FAQ, glossary, or hub page → auto-generated.
- **Daily blog:** A newsworthy event happened today and we want timely coverage. Captures timeliness.
- **Deep-dive blog:** A topic needs comprehensive, evergreen coverage on a specific workflow or concept (e.g., "Agentic Engineering Best Practices", "How to Use Claude Code Agent Teams"). Captures depth.
- **Cornerstone:** A flagship topic needs its primary authority page. Uses the deep-dive pipeline with a **cornerstone-specific skill prompt** (`skills/cornerstone-en/`, to be created) that produces a comprehensive overview covering all aspects rather than a single-angle deep-dive.

**Cluster pipeline routing rules:**
- Planner identifies a gap → determines content type → routes to the appropriate pipeline:
  - Gap is a compare, FAQ, or glossary page → `generate-seo.ts` (standard, automated)
  - Gap is a deep-dive blog → `write-topic-blog.ts` (queued for human approval, then run)
  - Gap is a cornerstone → `write-topic-blog.ts` with cornerstone skill (queued for human approval)
  - Gap is a topic hub → `generate-seo.ts` (standard, created last)

**System role:** Asset generation engine — generates content by page type and intent class, not by publication slot.

→ See: SPEC-05 (cornerstone), SPEC-06 (compare wave), SPEC-07 (FAQ wave), SPEC-08 (glossary)

### 4.5 LINK & VALIDATE

**Question: "How do we signal structure to search engines — and verify it's correct?"**

**Internal linking (hub-and-spoke):**
- Cornerstone ↔ every supporting page (bidirectional)
- Compare "A vs B" → Glossary entry for "B"
- FAQ "how to X" → Cornerstone section about X
- Topic Hub → everything (navigation index)
- Cross-cluster links where relevant

**Schema markup (JSON-LD) per page type:**

| Page Type | Required Schema |
|---|---|
| FAQ | `FAQPage` (targets PAA boxes) |
| Compare | `Article` with comparison metadata |
| Glossary | `DefinedTerm` (targets knowledge panels) |
| Cornerstone | `Article` + `BreadcrumbList` |
| Topic Hub | `Article` + `BreadcrumbList` |

**Link validation (post-generation QA):**
- After generating a page, automatically check every internal link
- Does the target page exist? If not, remove the broken link.
- Is there a term in the text that has a glossary page but wasn't linked? Flag it.

This stage had **no equivalent in the ChatGPT strategy** — it was identified by the Claude analysis as a critical gap.

→ See: SPEC-01 (technical SEO foundation), SPEC-08 (glossary linking pass)

### 4.6 MEASURE & REFRESH

**Question: "Is our content working? Is it still accurate?"**

**Performance monitoring:**
- GSC data: impressions, clicks, CTR, position — per page AND per cluster
- Cluster health: % of planned pages that exist, average position

**Two refresh trigger types:**
- **Event-driven:** Pricing change, new feature, deprecation → detected from news signals
- **Performance-driven:** Page dropping 3+ positions in rankings → detected from GSC data

**The key insight: it's a loop, not a line.** GSC queries with no landing page → new topic candidates. High-performing clusters → expand. Low-performing clusters → investigate. The refresh engine feeds back into DETECT.

**System role:** Refresh engine — detects staleness from both external events and performance degradation.

→ See: SPEC-09d (refresh detection), SPEC-10 (GSC pipeline), SPEC-11 (refresh execution), SPEC-14 (health dashboard)

## 5. Page Type Reference

| Type | Purpose | Intent | Schema | Creation Order | Min per Cluster |
|------|---------|--------|--------|----------------|-----------------|
| Cornerstone | Head-term anchor, primary ranking candidate | Navigational | `Article` + `BreadcrumbList` | 1st | 1 |
| Compare | Decision capture ("vs", "alternative to") | Commercial | `Article` + comparison metadata | 2nd | 5–7 |
| FAQ | Long-tail + PAA box capture | Informational | `FAQPage` | 3rd | 8–15 |
| Glossary | Concept definition, entity reinforcement | Definitional | `DefinedTerm` | 4th | 5–10 |
| Deep-dive blog | Workflow depth, advanced use cases | Informational | `Article` | Ongoing | 4–6 |
| Topic Hub | Cluster navigation, connects everything | Navigational | `Article` + `BreadcrumbList` | **Last** | 1 |

Each flagship topic should achieve this minimum shape plus explicit internal linking rules across the cluster.

### Cornerstone vs Topic Hub

These two page types are often confused. The key distinction:

| | **Cornerstone** | **Topic Hub** |
|---|---|---|
| Analogy | Wikipedia article | Table of contents |
| Purpose | Rank #1 on Google for the head term | Navigate and distribute link equity internally |
| Audience | External searcher ("what is claude code") | User already on the site exploring the cluster |
| Content | Deep, original, authoritative analysis (2000+ words) | Curated links + brief descriptions (1000–2000 words) |
| Created | **1st** in the cluster | **Last** in the cluster |
| SEO role | Attract organic traffic | Distribute authority across the graph |

**Example for Claude Code:**
- **Cornerstone:** "What is Claude Code? The Complete Guide (2026)" — comprehensive, content-rich, targets the head term
- **Topic Hub:** "Claude Code — All Coverage" — structured index of every article, compare, FAQ, and glossary page in the cluster

### Deep-dive blog production

Deep-dive blogs are produced by the `write-topic-blog.ts` pipeline (Gemini Deep Research → Narrative Architect → EN + ZH Writers). They are **supporting nodes** in the cluster graph — each covers one angle deeply (e.g., "Agent Teams", "Agentic Engineering Best Practices"), while the cornerstone covers all angles at overview level.

The same pipeline can produce cornerstone content by using a different skill prompt (comprehensive overview instead of single-angle deep-dive). Compare and FAQ pages use the standard SEO pipeline (`generate-seo.ts`) — the deep-dive pipeline is too costly for these shorter content types.

## 6. Flagship Topics & Rollout

### 6.1 Topic selection criteria

A topic qualifies as a flagship when it has:
- Enough content breadth and depth
- Enough ecosystem adjacency
- Enough compare richness and FAQ richness
- Enough update frequency to sustain the refresh loop

**Selection mechanism:** In Phases 1–3, flagship topics are selected manually by the human. In Phase 2+, the discovery engine surfaces topic candidates with strong signals (via the weekly discovery report), but the decision to invest in a full cluster treatment (20–30 coordinated pages) is always human-approved. The human can also inject topics manually at any time (e.g., "I noticed Harness Engineering is trending" → add as candidate).

### 6.2 Claude Code pilot

Claude Code is the **pilot template** — the first proving ground for the flagship-topic engine.

**4-layer cluster structure:**

| Layer | Content |
|---|---|
| A. Entry | What is Claude Code, complete guide, getting started, pricing |
| B. Workflow | Setup, installation, memory, CLAUDE.md, hooks, skills, agent teams, headless mode, CI/CD, monorepos, Docker |
| C. Comparison | vs Cursor, vs GitHub Copilot, vs Codex, vs Windsurf, vs Aider, vs Cline, vs Amazon Q Developer |
| D. Ecosystem | MCP, agents, skills, CLI vs MCP vs hooks, enterprise governance |

Cluster definition lives in `data/flagship-clusters/claude-code.json`.

→ See: SPEC-03 through SPEC-08

Second flagship topic. Already shows early demand, fits naturally into the Claude Code comparison universe, and can reuse the same cluster architecture.

Expansion order: Claude Code → Codex → MCP → selectively broaden into adjacent AI coding agent topics.

### 6.5 Rollout phases

### 6.6 Pilot success criteria

Claude Code is a successful flagship pilot when:
- Full minimum viable cluster coverage (1 cornerstone + 1 hub + 15 blogs + 7 compare + 12 FAQ + relevant glossary)
- Internal linking forms a connected graph (every node links to hub, hub links to all)
- Canonical and schema issues are resolved
- No 404s from old indexed URLs
- The cluster captures meaningful impressions and early clicks across multiple page types
- The planner can continue extending or refreshing it with low manual intervention

## 7. Multilingual Strategy

### English leads

English is the most information-dense upstream source layer for these topics. It is the best place to build the main topic graph, compare library, canonical glossary, and deepest technical content.

### Chinese is selective, not mirrored

Full mirroring would split operational focus, dilute authority-building effort, complicate indexing/canonical/internal-link governance, and risk creating shallow duplication rather than differentiated value.

### Chinese content focus

- High-value FAQ
- Localized comparisons
- Setup and workflow friction points
- Explanations and decision support
- Selective adaptation of English winners
- Original Chinese pages where local intent materially differs

- Raw signal utilization rate
- Asset queue throughput
- Page-type mix
- Refresh vs create ratio
- Dry-run vs published conversion

- **Schema coverage %** — % of published pages with correct JSON-LD for their type

- Answer-style query capture
- Schema coverage
- Extractable answer quality
- Citation-friendly page structure
- **Answer-first compliance** — % of FAQ/glossary pages where the first sentence is a direct, extractable answer

## 9. Distribution Engine

The cluster produces content (§4.4 CREATE). That content reaches users through multiple distribution channels, organized by maturity:

### 9.1 Current channels (operational)

| Channel | Mechanism | Frequency | Audience |
|---------|-----------|-----------|----------|
| **Organic search** | Cluster pages rank independently on Google | Always-on | Global search users |
| **Deep-dive blog** | 2,500–4,000 word posts via Gemini Deep Research pipeline | Ad-hoc (manual trigger) | Tech professionals seeking depth |
| **Daily blog** | 800–1,500 word news-driven posts from newsletter seeds | 1–3/day (automated) | Readers seeking timely coverage |
| **Newsletter** | Daily digest surfacing new + refreshed graph nodes | Daily EN + ZH | Subscribers |
| **Homepage** | Flagship topic entry points, recent additions | Always-on | Direct visitors |

Organic search through cluster pages is not "a" distribution channel — it is THE primary one. Newsletter, blog, and all other channels are amplification layers on top of the graph.

### 9.2 Near-term channels (high ROI, build next)

| Channel | Why | Effort |
|---------|-----|--------|
| **Twitter/X threads** | AI tech audience is highly active. Auto-generate thread summaries of deep-dive blogs. | Medium — needs thread generation skill + posting automation |
| **RSS feed** | Tech audiences rely on RSS readers. Easy to implement, compounds over time. | Low — Next.js RSS generation |
| **Social media cards** | Auto-generate Open Graph images optimized for sharing. Increases CTR on social. | Low — OG image generation |
| **Dev.to / Medium cross-posting** | Syndicate deep-dive content with canonical backlinks to LoreAI. Expands reach without diluting SEO. | Low — markdown export + canonical tags |
| **Reddit / Hacker News** | Submit flagship content to r/MachineLearning, r/ChatGPT, r/LocalLLaMA, HN. Manual curation for quality. | Low — manual, but high-impact for the right posts |

### 9.3 Medium-term channels (higher effort, high potential)

| Channel | Why | Effort |
|---------|-----|--------|
| **WeChat Official Account** | THE distribution channel for Chinese tech audience. LoreAI already produces ZH content. | Medium — account setup, content formatting, compliance |
| **YouTube Shorts / Reels** | AI-generated video summaries of blog posts. Visual content reaches different audiences. | High — video generation pipeline |
| **Podcast / audio** | TTS of deep-dive blogs as podcast episodes. Captures commute/workout time. | Medium — TTS pipeline + podcast hosting |
| **GitHub presence** | Example repos, tool comparisons, awesome-lists that link back to LoreAI content. | Low — but ongoing maintenance |

### 9.4 Long-term channels (ecosystem play)

| Channel | Why |
|---------|-----|
| **Community (Discord / forum)** | Build engaged audience around AI tool discussions. Content feeds community, community feeds content ideas. |
| **API / embed** | Let other tools embed LoreAI comparisons or FAQ answers. Becomes infrastructure. |
| **Partner syndication** | AI tool vendors link to LoreAI comparisons as neutral third-party analysis. |

### 9.5 Distribution principle

Every content node in the graph should be distributable through multiple channels with minimal extra work. The deep-dive blog is the clearest example: a single pipeline run produces a blog post (organic search), extracts SEO entities (feeds the cluster), generates a newsletter mention (subscriber reach), and can be reformatted as a Twitter thread, Dev.to post, or video script.

## Appendix A — Glossary of Terms

| Term | Definition |
|------|-----------|
| **Flagship topic** | A strategically selected topic that receives full cluster treatment (cornerstone + compare + FAQ + glossary + hub). |
| **Topic cluster** | A set of interlinked pages covering all search intents for a single topic. |
| **Cornerstone page** | The primary authority page for a topic's head term. 2000+ words, comprehensive. |
| **Topic hub** | A navigation/linking page that connects all pages in a cluster. Created last. |
| **Source grounding** | Generating content from real sources (docs, competitor analysis, community) rather than AI memory alone. |
| **AEO (Answer Engine Optimization)** | Structuring content so AI systems (ChatGPT, Perplexity, Google AI Overview) can extract and cite it. |
| **Graph planner** | The system component that decides which pages to create/refresh and in what order. |
| **Signal engine** | The system component that ingests and normalizes raw inputs into structured signals. |
| **Refresh trigger** | An event (news-driven) or performance signal (GSC-driven) that flags a page for content update. |
| **Hub-and-spoke linking** | Internal linking pattern where every spoke page links to the hub and the hub links to all spokes. |

## Appendix B — Decision Log

Resolved disagreements between the two source strategies, with rationale.

| # | Issue | Resolution | Reasoning |
|---|-------|-----------|-----------|
| 1 | **Topic Hub creation order** — ChatGPT listed hub alongside other page types without explicit ordering. Claude placed hub explicitly last. | **Hub is created LAST.** | A hub is a navigation/linking page. It cannot meaningfully link to pages that don't exist yet. Building it last ensures every spoke is available. |
| 2 | **Source grounding scope** — ChatGPT's strategy didn't address the quality gap between daily and cluster pipelines. Claude flagged this as a critical inconsistency. | **All factual content must be source-grounded**, regardless of which pipeline triggers generation. | The same content type (e.g., "Claude Code vs Cursor") should not have two quality tiers. Readers and search engines see the published page, not which code path produced it. |
| 3 | **Link validation as a pipeline stage** — ChatGPT's strategy had no post-generation validation step. Claude added LINK & VALIDATE as Stage 5. | **Link validation is a mandatory pipeline stage**, not optional QA. | Publishing broken internal links actively harms SEO (crawl waste, poor UX, lost link equity). Prevention is cheaper than cleanup. |
| 4 | **Newsletter's role** — Both strategies agreed newsletter should not gate SEO. ChatGPT framed it as "distribution engine." Claude framed it as "graph consumer." | **Newsletter is a graph consumer** that distributes, not a separate engine. | "Distribution engine" implies newsletter has its own planning logic. In practice, it should simply surface what the graph has produced. |
