## 1. Executive Thesis

LoreAI should evolve from a **newsletter-led publishing system** into a **flagship-topic-led keyword authority system**.

The system operates on two layers:

1. **Architecture layer (flagship-topic model):** Defines WHAT we build — which topics, what cluster structure, how pages link together. This is the E-E-A-T and AEO foundation. Flagship topics are manually curated.
2. **Execution layer (keyword-centric engine):** Defines WHAT TO BUILD NEXT — which keyword groups have the best ROI, what content type each needs, whether to create new or optimize existing. This drives week-over-week traffic growth.

The architecture layer provides structure. The execution layer provides velocity. Both operate simultaneously from day one.

The current system is strong at collecting information and producing daily content, but its long-term SEO/AEO potential is constrained because:

- SEO assets are structurally downstream of newsletter and blog selection.
- FAQ and compare generation have been starved relative to glossary generation.
- No topic currently has complete cluster coverage.
- Technical SEO issues are suppressing discoverability even when content quality is strong.
- There is no keyword-level tracking or opportunity-based prioritization.

The recommended strategic move is to:

1. **Demote newsletter from the main SEO gatekeeper to a downstream distribution layer.**
2. **Promote topic graph planning to the center of the content system.**
3. **Add a keyword-centric execution engine inside the topic graph architecture.**
4. **Use Claude Code as the first flagship topic template.**
5. **Use Codex as the second flagship topic after the Claude Code template is proven.**
6. **Run English as the primary authority layer and Chinese as a selective localized growth layer.**

The long-term goal is not "publish more content." It is to build a reusable system that can continuously:

- absorb raw signals,
- discover subtopics and expand keywords,
- prioritize by ROI (volume, competition, intent),
- generate the right content types,
- connect them into a coherent cluster,
- monitor keyword performance and refresh as needed,
- and compound SEO/AEO traffic over time.

## 2. Diagnosis

### 2.1 What LoreAI is already doing well

- High-volume multi-source ingestion
- A working daily publishing pipeline
- Multilingual publishing capability
- An emerging topic and keyword data layer
- Meaningful early Claude Code coverage
- Enough raw material to support a graph-led system

The problem is **not lack of content input**. The problem is that the output system is not yet optimized for flagship-topic authority.

### 2.2 Core bottlenecks

#### A — Serial dependency chain

Current flow is: **Collect → Newsletter → Blog → SEO**

This causes downstream starvation. If newsletter selection is narrow, or blog seed generation is narrow, then FAQ, compare, and topic assets are constrained even when the raw signal layer is rich.

#### B — Wrong production unit

LoreAI is still implicitly optimizing around "daily content production" rather than **keyword group coverage**. The correct production unit for long-term SEO/AEO is one keyword group → one page, organized within a flagship topic cluster.

#### C — Cluster imbalance

The existing system overproduces glossary pages relative to FAQ, compare, and topic hubs. That creates breadth without enough search-intent capture.

#### D — Technical SEO suppression

Technical issues reduce the upside of existing content. These issues are foundational rather than cosmetic and must be resolved before aggressive scale-up.

#### E — Inconsistent source grounding

The cluster pipeline generates pages from real sources (official docs, competitor content). The daily pipeline generates the exact same content types from AI memory alone — risking hallucinated features and pricing. Same content type, two quality levels, depending on which entry point triggered generation.

#### F — No link validation / post-generation QA

The system tells the AI to add internal links but never verifies whether those links point to real pages. If the AI invents a link to `/glossary/some-term` and that page doesn't exist, a broken link gets published.

#### G — No keyword-level prioritization

The system decides what to create based on content-type ordering (cornerstone first, then compare, then FAQ...) rather than keyword opportunity (volume, competition, intent). This means effort may be spent on high-competition keywords that can't rank while low-competition opportunities go uncovered.

### 2.3 Strategic implication

LoreAI should stop treating SEO assets as blog byproducts and instead treat them as **first-class graph nodes** generated by a keyword-aware planner that prioritizes by ROI.

### 2.4 GSC evidence

GSC 90-day data confirms the bottlenecks are real:

- **4 total impressions** for "what is claude code" at position 60–75
- Claude Code topic hub: **zero impressions**
- Compare pages: **not ranking**
- 34 FAQ pages: 397 impressions, **zero clicks**
- Blog is the only content type generating clicks (GPT-5.3 Codex SWE-bench post: 1,732 impressions alone)
- The highest-impression page (1,772 impressions) is a **404** from old `/en/` URLs

Despite having 19 blog posts, a topic hub, and glossary entries for Claude Code, the site captures near-zero Claude Code search traffic. This confirms: high-competition head terms are unreachable at current domain authority. The strategy must prioritize winnable keywords first.

## 3. North Star

> For each high-potential topic, LoreAI should become a clearly structured answer source across head terms, mid-funnel comparisons, long-tail FAQs, and concept definitions, with enough internal coherence that both search engines and LLMs can reliably understand, retrieve, and cite the site.

### 3.1 North-star outcomes

1. **Topic authority** — LoreAI becomes recognizably authoritative for a small set of target topics.
2. **Cluster completeness** — Each flagship topic has a coherent hub-spoke graph rather than isolated pages.
3. **Query coverage** — High-value informational, comparative, and definitional intents are systematically covered, prioritized by keyword ROI.
4. **AEO readiness** — Pages are structured to be extractable, quotable, and linkable in AI-generated answers:
  - **First-sentence-quotable answers:** FAQ and glossary content leads with a direct, extractable answer before elaboration.
  - **Feature tables for comparisons:** Compare pages use structured tables, not just prose — enabling AI systems to extract and cite specific feature differences.
  - **Schema types as structural requirements:** `FAQPage`, `DefinedTerm`, `Article`, and `BreadcrumbList` are not optional enhancements but mandatory structural signals for AEO.
5. **Compounding refreshability** — The system can detect when an existing node should be refreshed instead of creating endless new pages.

## 4. The Pipeline: Two-Layer Engine

The pipeline operates on two layers simultaneously:

- **Architecture layer** (flagship-topic model): defines cluster structure, page types, linking rules
- **Execution layer** (keyword-centric engine): decides what to build next, based on keyword opportunity

### 4.0 Concept Hierarchy

```
Level 1: FLAGSHIP TOPIC    →  "Claude Code" (manually curated)
Level 2: SUBTOPICS          →  "pricing", "vs Cursor", "hooks", "agent teams"
Level 3: KEYWORD GROUPS     →  {"claude code pricing", "claude code cost", "how much does claude code cost"}
Level 4: PAGES              →  /faq/how-much-does-claude-code-cost (one page per keyword group)
```

Every activity in the pipeline operates at one of these levels:


| Activity                                 | Operates at Level                   | Example                                        |
| ---------------------------------------- | ----------------------------------- | ---------------------------------------------- |
| Human curation                           | L1 (flagship topic)                 | "Let's cover Claude Code"                      |
| Official docs, Exa search, news entities | L2 (subtopics)                      | Discovers "agent teams" as subtopic            |
| GSC queries                              | L3 (keywords)                       | People found us via "claude code pricing 2026" |
| News events                              | L3 (keywords) with timeliness bonus | "Claude Code launches new pricing" → keyword   |


### 4.1 Pipeline Flow

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  FLAGSHIP TOPIC (manual curation)                           │
│      ↓                                                      │
│  SUBTOPIC DISCOVERY (automated: official docs, Exa,          │
│      |               news entities)                          │
│      ↓                                                      │
│  KEYWORD EXPANSION (automated: Serper PAA/related/auto,      │
│      |               GSC queries)                            │
│      ↓                                                      │
│  KEYWORD GROUPING (automated: cluster by shared intent)     │
│      ↓                                                      │
│  PRIORITY SCORING (volume × 1/competition × intent_value    │
│      |              + timeliness_bonus)                      │
│      ↓                                                      │
│  UNIFIED CREATE QUEUE (all content types, sorted by score)  │
│      ↓                                                      │
│  PAGE CREATION → LINK & VALIDATE → PUBLISH                  │
│      ↓                                                      │
│  PERFORMANCE MONITORING (weekly GSC review)                  │
│      ↓                                                      │
│  LOOP: new keywords → enter universe                        │
│        position changes → re-score priorities               │
│        striking distance → optimize existing                │
│        stale content → refresh                              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

Two weekly cycles drive the engine:


| Cycle                 | Cadence                                    | Purpose                   | Output                                              |
| --------------------- | ------------------------------------------ | ------------------------- | --------------------------------------------------- |
| **Discovery Cycle**   | Weekly (Saturday) + event-triggered        | Expand what we know about | New subtopics, new keywords, updated priority queue |
| **Performance Cycle** | Weekly (Tuesday, after GSC data refreshes) | Evaluate what we've built | Refresh/optimize actions for existing pages         |


Both feed into one **Unified Create Queue**, sorted by expected traffic impact.

### 4.2 Stage 1 — Flagship Topic Selection

**Question: "What topics deserve full cluster investment?"**

Flagship topics are **manually curated by the human**. A topic qualifies when it has:

- Enough content breadth and depth
- Enough ecosystem adjacency
- Enough compare richness and FAQ richness
- Enough update frequency to sustain the refresh loop

This is the only manual gate in the pipeline. Everything downstream is automated.

**System role:** Human decision. The discovery engine can surface candidate topics, but the decision to invest in a full cluster (20–30+ coordinated pages) is always human-approved.

### 4.3 Stage 2 — Subtopic Discovery

**Question: "What subtopics exist within this flagship topic?"**

For each flagship topic, automatically discover subtopics from three channels:


| Channel                                             | What It Discovers                                                   | Example                                                                                                             | Frequency |
| --------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------- |
| Official documentation structure                    | Natural topic anatomy (features, workflows, integrations)           | Anthropic docs have sections for hooks, skills, agent teams → each is a subtopic                                    | Weekly    |
| Exa semantic search (competitors + related content) | Coverage gaps and semantically related topics we haven't considered | Competitor has "Claude Code for monorepos" → subtopic gap; feed cornerstone URL → discovers "terminal AI workflows" | Weekly    |
| News pipeline entities                              | New developments worth covering                                     | "Anthropic launches Agent Teams" → new subtopic                                                                     | Daily     |


**Output:** Structured list of subtopics per flagship topic, each with source signals and discovery date. Persisted as `SubtopicPack` JSON artifacts in `data/flagship-packs/`.

> **Implemented (2026-03-27):** D1 Full Discovery synthesizes official docs + competitor content weekly; D1 Freshness routes daily news signals to approved subtopics. D2 ensures flagship subtopics are the authority source (`source='flagship_discovery'`) while entity extraction feeds `entity_extract` candidates separately.

### 4.4 Stage 3 — Keyword Expansion & Grouping

**Question: "What specific queries do people search, and which ones can a single page answer?"**

For each subtopic, expand into concrete keywords:

**Keyword expansion tools:**

- **Serper.dev:** PAA boxes ("People Also Ask"), related searches, autocomplete — Google's own view of what people search
- **GSC queries:** Real search queries that are reaching (or nearly reaching) our pages — actual demand data

**Keyword grouping:** Implemented as a **skill** (`skills/keyword-grouping/`). A single Claude call takes all expanded keywords for a subtopic and groups them by shared intent — if a user searching keyword A would be satisfied by the same page as keyword B, they belong in the same group → one page. The skill outputs grouped keywords with intent classification and suggested content type. Using a skill (rather than inline LLM call) makes the grouping prompt iterable, testable, and reusable across weekly discovery cycles.

Example for subtopic "pricing":

```
KEYWORD GROUP A (intent: "how much does it cost?")
├── "claude code pricing"
├── "claude code cost"
├── "how much does claude code cost"
├── "claude code pricing 2026"
└── → ONE PAGE: /faq/how-much-does-claude-code-cost

KEYWORD GROUP B (intent: "is there a free option?")
├── "is claude code free"
├── "claude code free tier"
├── "claude code free trial"
└── → ONE PAGE: /faq/is-claude-code-free
```

Each keyword group gets:

- **Primary keyword** (highest volume in the group)
- **Secondary keywords** (all others in the group)
- **Intent classification** (informational, commercial, definitional, navigational)
- **Estimated search volume** (from Serper/GSC)
- **Competition level** (from SERP analysis: low/medium/high/very high)
- **Assigned content type** (determined by intent + SERP analysis)

**Content type assignment by intent and SERP:**


| Intent                                   | SERP Signals                            | Content Type     | Research Pipeline |
| ---------------------------------------- | --------------------------------------- | ---------------- | ----------------- |
| Commercial ("vs", "alternative")         | Comparison tables ranking               | Compare page     | Standard          |
| Informational ("how to", "what is")      | Short answers / FAQ-style pages ranking | FAQ              | Standard          |
| Informational ("how to", "what is")      | Long-form guides (2000+ words) ranking  | Deep-dive blog   | Deep Research     |
| Definitional ("meaning", glossary terms) | Short definitions ranking               | Glossary entry   | Standard          |
| Navigational (head term)                 | Comprehensive guides ranking            | Cornerstone page | Deep Research     |
| Mixed/complex                            | Multiple content types ranking          | Deep-dive blog   | Deep Research     |


**The SERP depth signal is the key routing decision.** For informational keywords, the distinction between FAQ (Standard pipeline) and deep-dive blog (Deep Research pipeline) is determined by what's currently ranking — if top results are short answers, a focused FAQ competes; if top results are 2000+ word guides, only a deep-dive can compete. This signal is detectable automatically via Serper results + Exa `getContents` word count analysis.

**Deep Research weekly selection:** Among all keyword groups routed to Deep Research, the top 5 by priority score are built each week. The rest queue for the following week. No human approval needed — the priority formula and SERP depth signal together determine which deep-dives are most valuable.

**The cornerstone exception:** The cornerstone page targets multiple keyword groups because it's comprehensive. "What is Claude Code", "Claude Code guide", "Claude Code overview" are different keyword groups but all served by one cornerstone. This is the only page type that intentionally targets broadly.

→ See: SPEC-15 (discovery engine upgrade with Serper + Exa)

### 4.5 Stage 4 — Priority Scoring & Unified Queue

**Question: "What specific page do we build next?"**

Every uncovered keyword group is scored:

```
PRIORITY SCORE = volume × (1 / competition) × intent_multiplier + timeliness_bonus

Where:
  volume            = estimated monthly searches
  competition       = difficulty score (low=0.2, medium=0.5, high=1.0, very_high=2.0)
  intent_multiplier:
    commercial (compare)    = 3.0  (highest value — decision-stage users)
    informational (FAQ)     = 1.5  (good traffic, lower conversion)
    definitional (glossary) = 1.0  (useful for authority, low traffic)
    navigational (hub)      = 0.5  (internal use, not traffic-driving)
  timeliness_bonus  = 5000 if news event in last 48h, decays to 0 over 7 days
```

**This replaces the old fixed content-type ordering** (cornerstone first → compare → FAQ → glossary → hub). Instead, the queue is sorted by opportunity:


| Old Model (type-based)     | New Model (opportunity-based)                                       |
| -------------------------- | ------------------------------------------------------------------- |
| 1. Build cornerstone       | 1. Build whatever has highest priority score                        |
| 2. Build all compare pages | 2. Might be a low-competition FAQ, then a compare, then a deep-dive |
| 3. Build all FAQ pages     | 3. Cornerstone comes when domain authority makes it viable          |
| 4. Build all glossary      | 4. Topic hub still comes last (needs pages to link to)              |
| Fixed order                | Data-driven order                                                   |


**One constraint remains:** Topic hub is always last (it needs content to exist before it can link to it).

**Queue throughput & persistence:** The queue processes the top 10–20 pages per week (configurable). Unbuilt groups persist and are rescored each discovery cycle — priorities shift as new GSC data arrives or news events add timeliness bonuses. There is no minimum score threshold; scoring determines build **order**, not eligibility. Over time, this naturally progresses from high-value obvious pages to deeper long-tail coverage.

**Timely events are not a separate pipeline.** When a news event happens (e.g., "Anthropic announces new pricing"), it enters the keyword universe with a timeliness bonus that fast-tracks it to the top of the queue. The page is created through the same pipeline as any other page — it's just prioritized higher because of urgency. This replaces the old "daily blog" concept.

**Queue routing — two research pipelines × content skills:**

Every page is produced by combining a **research pipeline** (how deep we go) with a **skill** (how we write). The research pipeline determines source depth; the skill determines output format and style.


| Research Pipeline | How It Works                                                               | Cost                               |
| ----------------- | -------------------------------------------------------------------------- | ---------------------------------- |
| **Standard**      | Serper search → top URLs → Exa `getContents` → clean text → Claude + skill | Low (Serper + Exa + 1 Claude call) |
| **Deep Research** | Gemini Deep Research → multi-source synthesis → Claude + skill             | High (Gemini + Claude subagents)   |



| Content Type   | Research Pipeline | Skill               | Approval                                              |
| -------------- | ----------------- | ------------------- | ----------------------------------------------------- |
| Compare        | Standard          | `compare` skill     | Auto                                                  |
| FAQ            | Standard          | `faq` skill         | Auto                                                  |
| Glossary       | Standard          | `glossary` skill    | Auto                                                  |
| Topic Hub      | Standard          | `topic-hub` skill   | Auto (created last)                                   |
| News blog      | Standard          | `news-blog` skill   | Auto (timeliness bonus)                               |
| Deep-dive blog | Deep Research     | `deep-dive` skill   | Auto (within weekly budget)                           |
| Cornerstone    | Deep Research     | `cornerstone` skill | Auto (triggered when cluster completeness > 15 pages) |


**Deep Research budget:** Max 5 deep-dive calls per week. The priority queue determines which keyword groups get deep treatment — highest-scoring groups that need depth (detected by SERP analysis showing long-form content ranking) are auto-approved within budget. No human approval required. Cornerstone auto-triggers when a cluster has 15+ supporting pages.

### 4.6 Stage 5 — Page Creation

**Question: "How do we create trustworthy, high-quality content?"**

**Every page should be source-grounded.** The quality difference between "AI writes from memory" and "AI writes from real sources" is massive for SEO — search engines increasingly detect thin/hallucinated content. Both research pipelines (Standard and Deep Research) ensure this — no page is generated from AI memory alone.

**Two research pipelines:**


| Pipeline          | Flow                                                                | Word Count        | Cost |
| ----------------- | ------------------------------------------------------------------- | ----------------- | ---- |
| **Standard**      | Serper search → Exa `getContents` (full page text) → Claude + skill | 200–1,500 words   | Low  |
| **Deep Research** | Gemini Deep Research → multi-source synthesis → Claude + skill      | 2,500–4,000 words | High |


The Standard pipeline uses Serper to find relevant URLs, then Exa to fetch clean full-text content from those pages. This ensures Claude writes from real, current sources — not snippets or memory.

**Content type → pipeline + skill + AEO rules:**


| Content Type   | Pipeline      | Skill         | Word Count  | AEO Rule                                                                     |
| -------------- | ------------- | ------------- | ----------- | ---------------------------------------------------------------------------- |
| FAQ            | Standard      | `faq`         | 200–800     | Answer in the first sentence, then elaborate. Structure for AI extraction.   |
| Compare        | Standard      | `compare`     | 800–1,500   | Structured feature tables, not just prose. Lead with a clear verdict.        |
| Glossary       | Standard      | `glossary`    | 200–500     | One-sentence definition first. Precise, consistent entity mentions.          |
| Topic Hub      | Standard      | `topic-hub`   | 1,000–2,000 | Cluster navigation. Links to all supporting pages. Created last.             |
| News blog      | Standard      | `news-blog`   | 800–1,500   | Lead with the news event, then analysis. Timely and factual.                 |
| Deep-dive blog | Deep Research | `deep-dive`   | 2,500–4,000 | Workflow-oriented. Code examples where relevant.                             |
| Cornerstone    | Deep Research | `cornerstone` | 2,500–4,000 | Clear headings, direct answers at section tops. Comprehensive but scannable. |


**System role:** Asset generation engine — generates content by keyword group and intent, not by publication slot.

→ See: SPEC-05 (cornerstone), SPEC-06 (compare wave), SPEC-07 (FAQ wave), SPEC-08 (glossary)

### 4.7 Stage 6 — Link & Validate

**Question: "How do we signal structure to search engines — and verify it's correct?"**

**Internal linking (hub-and-spoke):**

- Cornerstone ↔ every supporting page (bidirectional)
- Compare "A vs B" → Glossary entry for "B"
- FAQ "how to X" → Cornerstone section about X
- Topic Hub → everything (navigation index)
- Cross-cluster links where relevant

**Schema markup (JSON-LD) per page type:**


| Page Type   | Required Schema                          |
| ----------- | ---------------------------------------- |
| FAQ         | `FAQPage` (targets PAA boxes)            |
| Compare     | `Article` with comparison metadata       |
| Glossary    | `DefinedTerm` (targets knowledge panels) |
| Cornerstone | `Article` + `BreadcrumbList`             |
| Topic Hub   | `Article` + `BreadcrumbList`             |


**Link validation (post-generation QA):**

- After generating a page, automatically check every internal link
- Does the target page exist? If not, remove the broken link.
- Is there a term in the text that has a glossary page but wasn't linked? Flag it.

This stage had **no equivalent in the ChatGPT strategy** — it was identified by the Claude analysis as a critical gap.

→ See: SPEC-01 (technical SEO foundation), SPEC-08 (glossary linking pass)

### 4.8 Stage 7 — Publish

All content flows through the same publish path:

1. `git commit + push` → triggers Vercel SSG rebuild
2. Page appears on loreai.dev
3. Newsletter (downstream consumer) scans for new/refreshed nodes and includes them in the daily digest

**Newsletter is a graph consumer, not a gatekeeper.** It reads from the published content graph and surfaces new or refreshed pages to subscribers. It does not control what gets created.

### 4.9 Performance Loop — Measure & Optimize

**Question: "How is what we built performing, and what should we do next?"**

The performance loop runs weekly (Tuesday, after GSC data refreshes with ~3-day lag) and produces actionable outputs.

**Step 1: Segment every tracked keyword by position range**


| Position    | Status                              | Action                                                            |
| ----------- | ----------------------------------- | ----------------------------------------------------------------- |
| 1–3         | Defending                           | Monitor weekly, don't touch unless dropping                       |
| 4–10        | Page 1, not top 3                   | Optimize content depth, improve title/meta for CTR                |
| 11–20       | **Striking distance** (highest ROI) | Add depth, improve internal links, refresh with current info      |
| 21–50       | Building                            | Build internal links from higher-ranking pages, add content depth |
| 50+         | Long shot                           | Don't optimize — build surrounding pages first, revisit later     |
| Not ranking | Uncovered                           | Create the page (enters priority queue)                           |


**Step 2: Detect anomalies**


| Anomaly                                   | Signal                                        | Action                                          |
| ----------------------------------------- | --------------------------------------------- | ----------------------------------------------- |
| High impressions, low CTR                 | Title/meta not compelling                     | Rewrite title and meta description              |
| High CTR, low impressions                 | Google not confident in authority             | Build internal links, create supporting content |
| Position dropping (3+ spots over 2 weeks) | Content getting stale OR competitors improved | Refresh content, check competitor changes       |
| New queries appearing in GSC              | Organic keyword discovery                     | Add to keyword universe, check coverage         |


**Step 3: Generate weekly action queue**

```
Priority A — STRIKING DISTANCE (position 11-20, highest ROI)
Priority B — CTR PROBLEMS (high impressions, low CTR)
Priority C — POSITION DROPS (was top 20, now declining)
Priority D — NEW COVERAGE (uncovered keywords with volume)
Priority E — NEW DISCOVERIES (GSC queries not in our universe)
```

**Step 4: Feed back into the engine**

- Priority A, B, C → **REFRESH actions** (update existing pages, enters create queue)
- Priority D → **CREATE actions** (new pages, enters priority scoring)
- Priority E → **RESEARCH actions** (new keywords enter subtopic/keyword discovery)

**Two refresh trigger types:**

- **Event-driven:** Pricing change, new feature, deprecation → detected from news signals → timeliness bonus
- **Performance-driven:** Position dropping, CTR problems → detected from GSC data → enters refresh queue

**The key insight: it's a loop, not a line.** GSC queries with no landing page → new keyword groups. Striking-distance pages → optimize. Dropping pages → refresh. The performance loop feeds back into the create queue continuously.

**System role:** Refresh engine — detects both keyword opportunities and content staleness.

→ See: SPEC-09d (refresh detection), SPEC-10 (GSC pipeline), SPEC-11 (refresh execution), SPEC-14 (health dashboard)

## 5. Page Type Reference


| Type           | Purpose                                     | Intent        | Schema                          | Min per Cluster |
| -------------- | ------------------------------------------- | ------------- | ------------------------------- | --------------- |
| Cornerstone    | Head-term anchor, primary ranking candidate | Navigational  | `Article` + `BreadcrumbList`    | 1               |
| Compare        | Decision capture ("vs", "alternative to")   | Commercial    | `Article` + comparison metadata | 5–7             |
| FAQ            | Long-tail + PAA box capture                 | Informational | `FAQPage`                       | 8–15            |
| Glossary       | Concept definition, entity reinforcement    | Definitional  | `DefinedTerm`                   | 5–10            |
| Deep-dive blog | Workflow depth, advanced use cases          | Informational | `Article`                       | 4–6             |
| Topic Hub      | Cluster navigation, connects everything     | Navigational  | `Article` + `BreadcrumbList`    | 1               |


**Creation order is determined by the priority scoring formula (§4.5), not by content type.** The only structural constraint: Topic Hub is always last (it needs pages to link to).

In practice, priority scoring naturally produces this order for a low-authority domain:

1. Low-competition FAQ and compare pages (highest ROI — winnable keywords)
2. Deep-dive blogs on uncovered niche subtopics (very low competition)
3. Higher-competition compare pages (as domain authority grows)
4. Cornerstone (when domain authority makes head terms viable)
5. Topic hub (last — needs content to link to)

As domain authority grows, the priority queue naturally shifts from long-tail toward mid-tail and eventually head terms. You don't manually decide "now it's time for head terms" — the formula does it as competition becomes relative to your improving authority.

Each flagship topic should achieve the minimum shape above plus explicit internal linking rules across the cluster.

### Cornerstone vs Topic Hub

These two page types are often confused. The key distinction:


|                   | **Cornerstone**                                      | **Topic Hub**                                        |
| ----------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| Analogy           | Wikipedia article                                    | Table of contents                                    |
| Purpose           | Rank #1 on Google for the head term                  | Navigate and distribute link equity internally       |
| Audience          | External searcher ("what is claude code")            | User already on the site exploring the cluster       |
| Content           | Deep, original, authoritative analysis (2000+ words) | Curated links + brief descriptions (1000–2000 words) |
| Keyword targeting | Multiple keyword groups (broad)                      | Not keyword-targeted (structural)                    |
| SEO role          | Attract organic traffic                              | Distribute authority across the graph                |


**Example for Claude Code:**

- **Cornerstone:** "What is Claude Code? The Complete Guide (2026)" — comprehensive, content-rich, targets the head term
- **Topic Hub:** "Claude Code — All Coverage" — structured index of every article, compare, FAQ, and glossary page in the cluster

### Deep-dive blog production

Deep-dive blogs and cornerstones use the **Deep Research pipeline** (Gemini Deep Research → Claude + skill). They are **supporting nodes** in the cluster graph — each covers one angle deeply (e.g., "Agent Teams", "Agentic Engineering Best Practices"), while the cornerstone covers all angles at overview level.

The same Deep Research pipeline produces both deep-dive and cornerstone content by using different skills (`deep-dive` skill for single-angle depth, `cornerstone` skill for comprehensive overview). All other content types (Compare, FAQ, Glossary, Topic Hub, News blog) use the **Standard pipeline** (Serper + Exa + Claude + skill) — the Deep Research pipeline is too costly for these shorter content types.

## 7. Multilingual Strategy

### English leads, Chinese follows for every page

English is the primary research and keyword expansion language. The unified queue operates in English. **Every page created in English also gets a Chinese version.** This ensures a consistent bilingual experience — the EN/ZH toggle on the site always works.

### Current approach: full bilingual coverage

Every page in the unified create queue produces both EN and ZH versions through the same pipeline:

```
CREATE EN page → CREATE ZH page → LINK & VALIDATE → PUBLISH both
```

- ZH content is **not translation** — it is independently written with a Chinese audience voice (WeChat-group tone, as per CLAUDE.md style guidelines)
- `hreflang` tags are added for every EN/ZH page pair
- Both versions share the same internal linking structure

This keeps the pipeline simple: no decision gate, no selective filtering. Every cluster page exists in both languages.

### Future: ZH localization layer

Once the bilingual pipeline is stable, a future improvement is to add a lightweight ZH keyword scan that discovers Chinese-specific search demand:

- ZH-original queries with no English equivalent (e.g., "Claude Code 国内能用吗")
- Localized search intent that differs from English (e.g., pricing in CNY, China-specific setup guides)
- These would create ZH-original pages that have no EN counterpart

This is deferred — not needed for the current rollout phases.

## 8. Measurement Model

### 8.1 Keyword-level metrics (execution layer)

The atomic unit of measurement is the **keyword group → page** pair:

- **Position** — current average position in Google (from GSC)
- **Impressions** — how often Google shows our page for this keyword
- **Clicks** — actual visits from this keyword
- **CTR** — clicks / impressions (compared to expected CTR for position)
- **Position trend** — improving, stable, or declining over 2-week windows
- **Coverage status** — covered (page exists) vs. uncovered (keyword group with no page)

### 8.2 Cluster-level metrics (architecture layer)

- **Cluster completeness score** — % of identified keyword groups that have a page
- **Keyword coverage by intent** — % of commercial, informational, definitional intents covered
- **Internal-link coverage** — every page links to hub, hub links to all
- **Proportion of orphaned nodes** — pages with no internal links pointing to them
- **Average position by content type** — are compare pages ranking better than FAQ? Why?
- **Striking distance count** — how many keywords in position 11-20 (optimization opportunities)

### 8.3 Pipeline-level metrics

- Raw signal utilization rate
- Asset queue throughput
- Create vs refresh ratio
- Dry-run vs published conversion
- **Link validation pass rate** — % of generated pages with zero broken internal links
- **Schema coverage %** — % of published pages with correct JSON-LD for their type
- **Priority queue accuracy** — do high-priority-score pages actually perform better?

### 8.4 AEO-oriented metrics

- Answer-style query capture
- Schema coverage
- Extractable answer quality
- Citation-friendly page structure
- **Answer-first compliance** — % of FAQ/glossary pages where the first sentence is a direct, extractable answer

## 9. Distribution

The cluster produces content (§4.6 CREATE). That content reaches users through multiple distribution channels:

### 9.1 Core channels


| Channel            | Mechanism                                          | Frequency     | Audience            |
| ------------------ | -------------------------------------------------- | ------------- | ------------------- |
| **Organic search** | Cluster pages rank independently on Google         | Always-on     | Global search users |
| **Newsletter**     | Daily digest surfacing new + refreshed graph nodes | Daily EN + ZH | Subscribers         |
| **Homepage**       | Flagship topic entry points, recent additions      | Always-on     | Direct visitors     |


Organic search through cluster pages is THE primary distribution channel. Newsletter and all other channels are amplification layers on top of the graph.

**Newsletter is a graph consumer.** It scans the content graph for new and refreshed pages, then surfaces them in the daily digest. It does not control what gets created. "Distribution engine" implies newsletter has its own planning logic. In practice, it should simply surface what the graph has produced.

## Appendix A — Glossary of Terms


| Term                                 | Definition                                                                                                                                     |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| **Flagship topic**                   | A strategically selected topic that receives full cluster treatment (cornerstone + compare + FAQ + glossary + hub). Manually curated by human. |
| **Topic cluster**                    | A set of interlinked pages covering all search intents for a single topic.                                                                     |
| **Subtopic**                         | A distinct aspect of a flagship topic (e.g., "pricing", "hooks", "vs Cursor" are subtopics of "Claude Code").                                  |
| **Keyword group**                    | A set of search queries that share one intent and can be satisfied by a single page. The atomic planning unit of the execution layer.          |
| **Keyword universe**                 | The complete set of all known keyword groups for a flagship topic. Continuously expanded by the discovery cycle.                               |
| **Priority score**                   | `volume × (1/competition) × intent_multiplier + timeliness_bonus`. Determines what to build next.                                              |
| **Striking distance**                | Keywords ranking position 11–20. Highest ROI for optimization — small improvements push to page 1.                                             |
| **Cornerstone page**                 | The primary authority page for a topic's head term. 2000+ words, comprehensive. Targets multiple keyword groups.                               |
| **Topic hub**                        | A navigation/linking page that connects all pages in a cluster. Created last.                                                                  |
| **Source grounding**                 | Generating content from real sources (docs, competitor analysis, community) rather than AI memory alone.                                       |
| **AEO (Answer Engine Optimization)** | Structuring content so AI systems (ChatGPT, Perplexity, Google AI Overview) can extract and cite it.                                           |
| **Graph planner**                    | The system component that decides which pages to create/refresh and in what order, driven by priority scoring.                                 |
| **Signal engine**                    | The system component that ingests and normalizes raw inputs into structured signals.                                                           |
| **Refresh trigger**                  | An event (news-driven) or performance signal (GSC-driven) that flags a page for content update.                                                |
| **Hub-and-spoke linking**            | Internal linking pattern where every spoke page links to the hub and the hub links to all spokes.                                              |
| **Discovery cycle**                  | Weekly automated process that expands the keyword universe (Saturday).                                                                         |
| **Performance cycle**                | Weekly automated process that evaluates keyword positions and generates refresh/optimize actions (Tuesday).                                    |
| **Timeliness bonus**                 | Priority score boost for keyword groups related to recent news events. Decays over 7 days.                                                     |
